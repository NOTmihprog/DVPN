# DVPN v4 — план развития

Цель: из «полносвязной P2P-сети с ручным обменом peers.json» сделать mesh-сеть:

- идентичность узла = публичный ключ (вместо `peer_id`);
- обязательное шифрование и аутентификация между узлами (сессии с PFS);
- группы узлов с ключом группы, состояние группы синхронизируется через сервер (и напрямую между узлами);
- mesh-маршрутизация с ретрансляцией через другие узлы (как EasyTier / Yggdrasil);
- маршрутизация подсетей по ключам узлов (CKR, как в `Yggdrasil-ng/docs/CKR.md`);
- автоматическая синхронизация маршрутов (как `yggmgr`);
- IPv6 в underlay (транспорт) и в overlay (TUN);
- статические соединения (узлы с известным адресом, без трекера);
- корректный TTL / Hop Limit и работающий traceroute через ретрансляторы (в CKR Yggdrasil-ng TTL транзитного трафика не меняется);
- **сохраняется главная особенность DVPN: у узла ровно один UDP-сокет** — через него идёт всё: трекер, пиры, ретрансляция, статические пиры, IPv4 и IPv6.

v4 — несовместимый переход с v3: совместимость протокола, API и форматов файлов не поддерживается, сеть переводится целиком.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Кодирование ключей | base64url без паддинга (43 символа), везде: конфиг, CLI, API, логи |
| Маршрутизация и группы | изолирована внутри каждой группы, транзита между группами нет |
| Сервер видит `group_id` и ключи участников | да — трекер проверяет подписи и сертификаты членства |
| Совместимость с v3 | не нужна (ни протокол, ни API, ни `peers.json`, ни миграция) |
| Сокеты | один UDP-сокет на узел (dual-stack); никаких дополнительных транспортов и сокетов |
| TTL | ретрансляторы уменьшают TTL/Hop Limit, источник генерирует ICMP Time Exceeded от их имени (§6.4) |
| Членство в группе | сразу сертификаты (`MemberCert`) с ролями, режима «общий секрет у всех» нет |

Документ состоит из: анализа текущего кода, модели угроз, целевой архитектуры, протоколов, этапов внедрения и списка того, что лучше переделать.

## Модель угроз

От кого защищаемся и чем. Строки — это чек-лист: каждая мера должна быть реализована и покрыта тестом.

### Злонамеренный участник группы (есть валидный сертификат)

| Угроза | Мера |
|---|---|
| Врёт в LSA (рисует несуществующие рёбра, чтобы притянуть чужой трафик) | ребро учитывается, только если **оба** конца его подтвердили (двусторонняя проверка, §6.2); LSA подписан origin |
| Анонсирует чужие/публичные префиксы (угон подсети, фальшивый exit) | `allowed_prefixes` в сертификате (§5.2): узел может анонсировать только выданное админом; конфликт префиксов отклоняется |
| Отбрасывает/искажает транзит | сквозное шифрование A↔C (§4.3) — ретранслятор не может подменить данные; при потерях маршрут уходит на другой путь (метрика) |
| Флудит состоянием/LSA | лимит частоты и размера на соседа; версии монотонны (старое не переписывает новое) |
| Нагружает чужой relay | лимиты ретрансляции (§11.2), роль `relay` в сертификате |
| Обходит доступ к сервисам других узлов | ACL группы (§7.4) |

### Злонамеренный или любопытный трекер

| Угроза | Мера |
|---|---|
| Читает состояние сети (маршруты, подсети) | записи зашифрованы `group_enc` (§5.4); трекер видит только `group_id`, ключи и зашифрованные blob'ы (это принятый компромисс) |
| Подделывает записи состояния | каждая запись подписана автором; подпись проверяется узлами и самим трекером |
| Скрывает записи / отдаёт устаревшие | тот же gossip идёт напрямую между узлами (§5.4/§8.2) — трекер не единственный источник; расхождение версий заметно |
| Подсовывает ложные endpoint-ы (MITM-попытка) | endpoint лишь адрес для punch; сессия всё равно требует Noise с `group_psk`/сертификатом — подделанный endpoint не даёт прочитать трафик |
| Угоняет чужой онлайн-статус/endpoint | `Announce` подписан ключом узла над транскриптом (§11) |

### Наблюдатель на канале (DPI, цензор)

| Угроза | Мера |
|---|---|
| Блокировка по сигнатуре пакета | маскировка (§4.4): нет статических байт, полей длины, фиксированных размеров |
| Вычисление трекера по единому сокету | маскировка трекер-сессии (§11.1) |
| Активное зондирование (повтор перехваченного handshake) | timestamp + replay-окно, трекер и пир не отвечают на повтор (§11.1) |
| Корреляция по таймингам/размерам | случайные тайминги и паддинг по умолчанию (§4.4) |

### Локальный злоумышленник на узле

| Угроза | Мера |
|---|---|
| Кража приватного ключа/секрета группы из файла | права `0600` на `config.toml` (на Windows — ACL владельцу); секрет группы — только у админов (§доп.) |
| Потеря всех админских ключей → группа замирает | бэкап админ-ключей, ≥2 админа (§доп.) |

### Вне модели (честно)

- Компрометация эндпоинта (root на машине узла) — не защищаемся.
- Мимикрия под конкретный разрешённый протокол (против whitelist-DPI) — вне рамок v4 (§4.4).
- Анонимность состава сети от трекера — сознательно не цель (принятое решение).

## 1. Что есть сейчас (v3.0.0) и что мешает

| Компонент | Сейчас | Проблема для целей v4 |
|---|---|---|
| `peer_id.rs` | 32 случайных ASCII-символа | Знание id = право анонсировать его на трекере. Любой участник может «угнать» endpoint другого узла. Id не связан с криптографией. |
| `crypto.rs` `PeerCipher` | Ключ **получателя**, XChaCha20-Poly1305, случайный nonce | Все, кто шлёт узлу X, знают ключ X → любой из них может выдать себя за любого другого отправителя. Нет аутентификации отправителя, нет PFS, нет ротации ключей. 41 байт накладных расходов на пакет. |
| `proto.rs` `PLAIN` | Пакеты без шифрования, если у получателя нет ключа | Шифрование опционально → его нужно убрать. |
| Определение отправителя | По UDP-адресу источника (`by_endpoint`) | Не работает для ретрансляции; роуминг сделан через «попробовать расшифровать маленький пакет своим ключом» (`ROAM_MAX_LEN`). |
| Трекер | Announce/Search/Found, найденные пары = взаимный Search | Трекер не проверяет, что клиент владеет id. Взаимный поиск требует, чтобы оба знали друг друга заранее. |
| `storage.rs` | `peers.json`: id, name, addr(IPv4), key | Один IPv4 на узел, подсетей нет, синхронизация — ручной export/import. |
| `node.rs` TUN | Только IPv4, `dst → peer` точным совпадением, проверка `src == peer.addr` | Нет LPM-таблицы, нет IPv6, нет маршрутов «через узел». |
| `transport.rs` | Один UDP-сокет IPv4 | Нет IPv6 underlay, нет статических портов/адресов как полноценной сущности. |
| Маршрутизация | Только прямые линки | Если hole punching не удался (симметричный NAT с обеих сторон) — связи нет. |

Что хорошо и стоит сохранить:

- один сокет для трекера и пиров (нужен для hole punching);
- подписанный handshake с трекером (сервер аутентифицирован Ed25519);
- `ReplayWindow`, паддинг HELLO против амплификации, случайный паддинг keepalive;
- `toml_edit` с сохранением комментариев;
- API поверх msgpack (оставить, но расширить и версионировать).

## 2. Целевая архитектура

```
              ┌──────────── трекер (rendezvous + реплика состояния + relay последней надежды) ───────────┐
              │  сессии узлов (аутентифицированы ключом узла), индекс group_id → онлайн-участники,       │
              │  зашифрованные записи состояния групп (сервер их не читает)                               │
              └───────────────▲──────────────────────────────▲──────────────────────────────▲────────────┘
                              │ UDP v4/v6, маскированный      │                              │
   ┌──────── узел A ──────────┴──┐        ┌──────── узел B ───┴─────────┐        ┌──── узел C ┴────┐
   │ identity (Ed25519)          │ obfs+  │                             │ obfs+  │                 │
   │ obfs: маскировка пакетов    │ Noise  │                             │ Noise  │                 │
   │ links: сессии с соседями    │◄──────►│ links                       │◄──────►│                 │
   │ router: LSDB + Dijkstra     │        │ router (relay A↔C)          │        │                 │
   │ ckr: prefix → node key      │        │ ckr                         │        │                 │
   │ state: подписанные LWW      │◄─sync─►│ state                       │◄─sync─►│                 │
   │ plan → TUN адреса, маршруты,│        │ plan → NAT/forwarding (exit)│        │                 │
   │        NAT, failover        │        │                             │        │                 │
   │ TUN (IPv4+IPv6) / API       │        │                             │        │                 │
   └─────────────────────────────┘        └─────────────────────────────┘        └─────────────────┘
```

Слои (снизу вверх):

1. **Transport** — единственный UDP-сокет `[::]:port` (dual-stack). Трекер отделяется по адресу источника (адреса трекеров известны), остальное — по индексу сессии.
2. **Obfs** — маскировка: на проводе только байты, неотличимые от случайных, со случайными размерами и таймингами. Пассивный наблюдатель без ключа группы не видит сигнатур, активный зонд не получает ответа (§4.4).
3. **Link** — сессия Noise с *соседом* (тот, с кем есть прямой путь), keepalive, RTT, роуминг.
4. **Router** — link-state маршрутизация (LSA + Dijkstra), пересылка пакетов через соседей.
5. **Session (e2e)** — для трафика через ретрансляторы: сквозная сессия Noise между отправителем и получателем. Для соседа link-сессия и e2e-сессия — одна и та же.
6. **CKR** — таблица `префикс → ключ узла`, проверка источника входящих пакетов.
7. **State + Sync** — реплицируемое подписанное состояние группы (узлы, адреса, подсети, настройки), синхронизация через трекер и напрямую.
8. **Plan/Apply** — из состояния детерминированно строится CKR, системные маршруты, адреса TUN, NAT для шлюзов.

### 2.1. Почему link-state (EasyTier), а не spanning tree (Yggdrasil)

| | Yggdrasil (дерево + greedy + bloom) | EasyTier (OSPF-подобный link-state) |
|---|---|---|
| Масштаб | десятки тысяч узлов, глобальная сеть | сотни-тысячи узлов |
| Оптимальность пути | субоптимально (через дерево) | кратчайший путь по метрике (RTT) |
| Сложность | высокая (ironwood ~7.6k строк) | средняя |
| Состояние на узле | O(соседи + пути) | O(N узлов + рёбра) |
| Подходит для приватных групп | избыточно | да |

DVPN — приватные сети из десятков-сотен узлов. **Рекомендация: link-state.** Каждая сеть (группа) — свой домен маршрутизации; глобальной сети, как у Yggdrasil, нет. Из Yggdrasil берём: ключ как адрес, CKR, синтаксис префиксов, адрес IPv6, производный от ключа.

## 3. Идентичность: ключ вместо `peer_id`

- Узел хранит один секрет — **Ed25519 seed** (32 байта) в `config.toml` (`[identity] private_key`), либо из env `DVPN_PRIVATE_KEY`.
- `NodeId` = Ed25519 public key (32 байта). Для Noise ключ конвертируется в X25519 (как в Yggdrasil: `ed25519 → curve25519`), второй секрет не нужен.
- Текстовая форма: **base64url без паддинга, 43 символа** (`encode_b64` → `URL_SAFE_NO_PAD`; при разборе принимать и standard, и с паддингом, как сейчас `decode_b64`). В CLI/логах — короткий префикс (8–10 символов) + имя узла; полный ключ по уникальному префиксу, как сейчас `storage.find(prefix)`.
- Логгер (`logger.rs`) ищет id в тексте сообщений — вместо эвристики логировать через `Display` обёртки `NodeId`, которая сама выводит `имя(префикс)`.
- `PeerId` в коде заменяется на `NodeId([u8; 32])` с `Display`/`FromStr`/`Serialize`; модуль `peer_id.rs` → `identity.rs` (`Identity { signing: SigningKey, x25519: StaticSecret }`, `NodeId`).

Миграции нет: узлы v4 создаются заново (`dvpn gen-key`, `dvpn group join`).

## 4. Обязательное шифрование и маскировка

Криптографию берём из WireGuard, а формат на проводе делаем свой и маскированный (§4.4): никакого фиксированного первого байта, предсказуемых длин и mac-полей, по которым DPI ставит сигнатуру. Байтовые константы ниже (`0x20`…) — это *логическое* обозначение типа сообщения для описания; на провод они выходят зашифрованными слоем obfs.

### 4.1. Handshake

`Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s` (криптосхема WireGuard):

- **I** — инициатор отправляет свой статический ключ (зашифрованно);
- **K** — статический ключ ответчика известен заранее (из состояния группы, от трекера или из конфига статического пира);
- **psk2** — общий секрет группы (`group_psk`, см. §5), без него handshake не пройдёт. Узел вне группы не может даже начать сессию.

Эфемерный публичный ключ X25519 кодируется **Elligator2** (представление точки неотличимо от случайной 32-байтовой строки) — иначе первые 32 байта handshake статистически отличались бы от случайных, и это стало бы сигнатурой. В WireGuard эфемерный ключ идёт «как есть».

**Elligator2 нужно делать аккуратно** (ошибки early-obfs4 обходятся так):

- отображаемы не все точки кривой; при генерации эфемерной пары ключ перегенерируется в цикле, пока точка не имеет представления (вероятность успеха ~1/2 на попытку);
- 254-битное представление дополняется до 256 бит **двумя случайными старшими битами** — иначе старшие биты всегда нулевые и это сигнатура;
- точки малого порядка и знак `v`-координаты рандомизируются;
- декодирование (`representative → point`) и кодирование должны быть константного времени.

**Реальность API:** в `curve25519-dalek` 5.0 `elligator_encode` есть, но он `pub(crate)` (приватный), публичного инверсного отображения и перегенерации нет. Поэтому Elligator2-слой придётся либо брать из отдельного crate (проверить `curve25519-elligator2` — его использует Tor/arti), либо реализовать поверх field-арифметики самому. Это отдельная задача с тестовыми векторами obf4/arti, её нельзя считать «просто вызвать функцию».

Реализация handshake (решено на этапе 2): своя реализация IKpsk2 на `x25519-dalek`/`chacha20poly1305`/`blake2` (как `noise-protocol.go` в amneziawg-go), транспорт без состояния (явный nonce = счётчик, пакеты UDP приходят не по порядку). Риск снят сверкой со `snow` в тестах: обе стороны в обе стороны, хэш handshake и транспортные ключи совпадают. Эфемерные ключи передаёт вызывающий — так Elligator2 (`curve25519-elligator2`) подставляет отображаемые ключи; кодирование/снятие — в `obfs.rs`.

Payload handshake: timestamp TAI64N (защита от replay первого сообщения), `group_id`, сертификат членства (§5), версия протокола, флаги возможностей (relay, exit, IPv6).

### 4.2. Транспортные пакеты (wire v4, логический вид до маскировки)

```text
HS_INIT    [0x20][sender_idx u32][eph (Elligator2) 32][enc static][enc payload]
HS_RESP    [0x21][sender_idx u32][receiver_idx u32][eph (Elligator2) 32][enc payload]
COOKIE     [0x22][receiver_idx u32][nonce 24][enc cookie]       (защита от DoS, этап 8)
DATA       [0x23][receiver_idx u32][counter u64][ciphertext][tag 16]
```

Внутри `DATA` (plaintext):

```text
[kind u8][...]
kind 0  KEEPALIVE / PING / PONG    (RTT, liveness)
kind 1  IP-пакет (IPv4 или IPv6)   → TUN
kind 2  ROUTING                    (LSA sync, §6)
kind 3  STATE                      (синхронизация записей состояния, §8)
kind 4  FORWARD                    [limit u8][hops u8][probe u16][dst NodeId 32][вложенный пакет HS_*/DATA для dst]
kind 5  ICMP_REPORT                [probe u16][reporter NodeId 32][code u8]   (§6.4)
kind 32..=255  API-маршруты        (как сейчас ROUTE_API_MIN..MAX)
```

- **receiver_idx** — случайный 32-битный индекс сессии (как в WireGuard). Получатель находит сессию без перебора ключей и без привязки к UDP-адресу.
- **Роуминг**: если аутентифицированный `DATA` пришёл с нового адреса — endpoint соседа обновляется. Хак с `ROAM_MAX_LEN` и `sender_id` в control-пакетах удаляется.
- **Rekey**: новый handshake каждые 120 с или 2^60 сообщений (как WireGuard), старая сессия живёт ещё 1 интервал.
- Накладные расходы прямого пакета: 1+4+8+16+1 = **30 байт** (сейчас 42).
- `PLAIN`, `PeerCipher`, `key` в записях пиров — удаляются. Отключить шифрование нельзя.

### 4.3. Ретрансляция и сквозное шифрование

Пакет A → C через B:

```
A: inner = DATA(сессия A↔C)           — B не может прочитать
A: outer = DATA(сессия A↔B, kind=FORWARD, ttl, dst=C, inner)
B: расшифровывает outer, видит dst=C, ttl-1, заворачивает inner в DATA(сессия B↔C, FORWARD)
C: расшифровывает outer (B↔C), затем inner (A↔C) → по receiver_idx знает, что отправитель A
```

- Handshake A↔C тоже идёт внутри `FORWARD`, поэтому сквозная сессия возможна без прямого UDP-пути.
- Внешний слой (link-сессия) гарантирует, что ретранслятор принимает только от соседей по группе — посторонние не могут использовать узел как открытый relay.
- Двойное шифрование только на ретранслируемых путях; на прямом пути — одно.
- После установления сквозной сессии через relay узлы параллельно пробуют прямое соединение (hole punching через трекер, известные endpoint из LSA) — как «on-demand P2P» в EasyTier.

### 4.4. Маскировка трафика от DPI

Цель — анти-цензурная маскировка, как у AmneziaWG (`amneziawg-go`), obfs4 и pluggable transports Tor: защитить **свой же** трафик от блокировки по сигнатуре. Требование строже, чем у WireGuard: **на проводе не должно быть ни одного статического байта, предсказуемого поля длины или фиксированного размера пакета**. Для пассивного наблюдателя без ключей группы поток — просто UDP со случайным содержимым и случайными размерами; активный зонд, повторивший перехваченный пакет, ответа не получает (timestamp + replay-окно).

Параметры маскировки общие для группы (часть профиля в invite, §5.3), чтобы все участники выглядели одинаково и могли понять друг друга. Профиль версионируется, чтобы его можно было менять, если конкретная сигнатура начала блокироваться.

**Окно перехода при смене профиля.** Новый профиль (или `psk_epoch`, §5.2) распространяется записью состояния и доходит до узлов не одновременно. Если переключиться резко, узлы со старым и новым профилем перестанут понимать друг друга и сеть расколется. Поэтому:

- запись-профиль несёт `active_from` (момент HLC, с запасом вперёд) и держит **оба** набора параметров — текущий и следующий;
- до `active_from` узлы **принимают** пакеты, замаскированные любым из двух профилей, а **отправляют** ещё старым; после — отправляют новым, но продолжают принимать старый ещё один интервал (grace);
- для входящего пакета, который ещё не привязан к сессии, узел пробует снять маску обоими профилями (их 1–2, перебор дешёвый);
- то же для `psk`: в окне перехода handshake пробуется с psk обеих эпох.

Так смена сигнатуры или ключа проходит без разрыва связи.

**Из AmneziaWG берём (параметры — в `[obfs]` профиля группы):**

| Параметр | Назначение |
|---|---|
| `jc` / `jmin` / `jmax` | `jc` junk-пакетов случайного размера `jmin..jmax` перед handshake — замусоривают начало потока |
| `i1..i5` | пакеты-сигнатуры перед handshake, собираются из тегов: `<b 0x..>` статические байты, `<r N>` случайные, `<rc N>` случайные буквы, `<rd N>` случайные цифры, `<t>` timestamp. Позволяют имитировать начало какого-нибудь безобидного протокола |
| `s1..s4` | паддинг init / resp / cookie / data-сообщений |
| `h1..h4` | диапазоны значений для «типа сообщения» каждого вида (вместо фиксированных `0x20..0x23`) |
| `header_protection_key` | защита заголовка: ChaCha20 (unauthenticated) шифрует низкоэнтропийные поля заголовка (индексы, счётчик), чтобы они не выделялись |
| `content_padding` | случайный доп. паддинг данных |
| тайминги-диапазоны | `rekey_after`, `rekey_timeout`, `keepalive` и т.п. заданы диапазонами, а не константами — убирает периодичность |
| `random_trailers` | случайный «хвост» пакета |

**Строже, чем AWG (это выбор DVPN, а не копия):**

1. **Нет фиксированного первого байта.** AWG всё равно оставляет `uint32` тип в начале (пусть и в диапазоне `h1..h4`); в DVPN «тип» выводится из первых байт через `header_protection_key` и становится неотличим от случайного. Мультиплексирование трекер/handshake/data делается по индексу сессии после снятия защиты заголовка, а не по открытому полю.
2. **Elligator2 для эфемерных ключей** (§4.1) — у AWG их нет, и 32 байта ключа в handshake статистически отличимы от случайных.
3. **Нет фиксированных размеров.** HELLO/HELLO_ACK у v3 были ровно 128/97 байт; в v4 каждый пакет получает случайный паддинг, а junk/signature-пакеты ломают гистограмму размеров первых пакетов сессии.
4. **Случайные тайминги по умолчанию,** а не опционально.

**Границы (честно о том, чего маскировка не делает):**

- Это маскировка «выглядит как случайный UDP / неизвестный протокол», а не имитация конкретного разрешённого протокола (QUIC, DTLS). Против whitelist-фаервола («разрешён только трафик, похожий на HTTPS») нужен отдельный транспорт-мимикрия — вне рамок v4, но профиль `[obfs]` оставляет место для него на будущее (этап 8).
- Паддинг не должен делать пакет больше MTU пути — иначе фрагментация сама по себе подозрительна (предупреждение из README AWG); при расчёте overhead (§6.4, §17) паддинг учитывается и ограничивается.
- Junk/signature-пакеты и паддинг стоят трафика и CPU — профиль по умолчанию умеренный (`jc=4..8`), агрессивный режим включается в сетях с активной цензурой.

**Модуль:** `obfs.rs` — кодирование/декодирование кадра (защита заголовка, паддинг, Elligator2-обёртка), генератор junk/signature-пакетов, разбор профиля. Он оборачивает `transport.rs` на отправке и первым обрабатывает входящий датаграм на приёме, до определения типа.

## 5. Группы

### 5.1. Ключи группы

Группа задаётся **секретом группы** (32 байта, «приватный ключ группы»). Из него через HKDF выводится:

```text
group_secret ─┬─ HKDF "dvpn/4 group sign" → Ed25519 group_sign_key → group_pub = group_id
              ├─ HKDF "dvpn/4 group psk"  → group_psk   (psk в Noise, §4.1)
              └─ HKDF "dvpn/4 group state"→ group_enc   (шифрование записей на сервере)
```

- `group_id` = `group_pub` — публичный; по нему трекер индексирует группу и **может проверять подписи**, не зная секрета.
- Узел может состоять в нескольких группах. Сессия между двумя узлами допустима, если у них есть общая группа (psk выбирается по `group_id` из payload handshake).
- Адресные пространства разных групп не должны пересекаться (проверка при вступлении); маршрутизация — отдельная на каждую группу, транзит между группами только явно (будущий «gateway между группами»).

### 5.2. Роли и сертификаты (с первой версии)

Режима, где каждый участник знает `group_secret` (как `network_secret` в EasyTier), нет: исключить участника в нём можно только сменой секрета у всех.

- **Администраторы** хранят `group_secret` (могут подписывать).
- **Участники** получают: `group_psk`, `group_enc` и **сертификат членства**, подписанный `group_sign_key`:
  ```text
  MemberCert { group_id, node: NodeId, name, roles: [relay, exit_v4, exit_v6, admin],
               allowed_prefixes: [IpNet], not_after, serial, sig }
  ```
- Сертификат проверяется в handshake (передаётся в payload) и трекером при Announce.
- `allowed_prefixes` — защита от угона префиксов: узел может анонсировать только то, что ему выдал админ.
- Исключение участника: подписанная запись-отзыв (`revoke serial`) + ротация `group_psk` по эпохам (`psk_epoch` в состоянии, новый psk раздаётся участникам в зашифрованных записях). Смена эпохи идёт с окном перехода (§4.4): в окне handshake принимается с psk обеих эпох, иначе исключение одного узла временно отрезало бы ещё не обновившихся.
- Продление: сертификаты короткоживущие (например 30 дней), узел заранее запрашивает новый у любого онлайн-админа через состояние группы; при недоступности админов действующий сертификат работает до `not_after`.
- Первый админ — создатель группы; админ может выдать роль `admin` другому узлу (такой узел получает `group_secret` в зашифрованной записи, адресованной его ключу). Рекомендуется ≥2 админа, чтобы потеря одного узла не блокировала группу.

#### Смена `psk_epoch` без раскола сети

Новый psk расходится по группе не мгновенно: часть узлов офлайн, часть получит запись через минуты. Если в момент смены все сразу перейдут на новый psk, узлы с разными эпохами перестанут понимать друг друга. Поэтому смена ид

### 5.3. Вступление в группу

```
dvpn group create --name home                     → печатает group_secret (админ)
dvpn group invite --group home [--name laptop] [--prefix 10.10.0.5/32] [--ttl 24h]
      → invite-токен: group_id, group_psk, group_enc, адреса трекеров + ключи, (cert либо одноразовый join-ключ)
dvpn group join <invite>
```

Invite — base64url-строка (и QR в будущем). Одноразовый join-ключ позволяет новому узлу самому прислать свой публичный ключ, а админ-узел (любой онлайн) выпустит сертификат автоматически.

### 5.4. Синхронизация группы через сервер

Трекер становится **репликой состояния группы, которая не может его прочитать**:

- узлы кладут на трекер подписанные записи, зашифрованные `group_enc` (`StatePut`);
- трекер хранит `group_id → {record_id_hash → (version, blob)}`, проверяет только подпись автора (если включены сертификаты — что автор член группы);
- узел при подключении сравнивает сводку версий (`StateSummary`) и забирает недостающее (`StateGet`);
- тот же обмен идёт напрямую между узлами (kind 3 `STATE`), поэтому сеть работает и при недоступном трекере (как gossip в yggmgr).

Хранение на трекере — файл/sqlite с квотой на группу; записи без обновлений дольше N дней удаляются.

## 6. Mesh-маршрутизация (link-state)

### 6.1. LSA (анонс узла)

Каждый узел периодически (30 с) и при изменении публикует подписанный своим ключом анонс:

```text
Lsa {
  origin: NodeId, group_id, seq: u64 (монотонный, HLC), expires: секунды,
  neighbors: [(NodeId, cost: u32, flags)],   // cost = сглаженный RTT мс + штрафы за потери
  endpoints: [SocketAddr],                   // свои публичные/локальные адреса (для прямых попыток)
  flags: can_relay, nat_type,
  sig
}
```

- Префиксы (CKR) **не** входят в LSA — они в медленном состоянии (§8). Маршрутизация (быстрая, часто меняется) и конфигурация (медленная, долго живёт) разделены.
- Рассылка: синхронизация сводок `(origin, seq)` с соседями по link-сессиям (kind 2), передаются только новые LSA. Устаревшие (expires) удаляются из LSDB.
- Защита: подпись origin, origin должен быть участником группы, ограничение размера/частоты.

### 6.2. Расчёт маршрутов

- Граф: рёбра берутся, только если оба конца подтверждают соседство (двусторонняя проверка, как в OSPF) — нельзя «нарисовать» себе ребро.
- Dijkstra с запоминанием первого хопа (`dijkstra_with_first_hop` в EasyTier) → `next_hop[dst]`.
- Узлы без `can_relay` не используются как транзитные.
- Гистерезис: новый путь заменяет старый, только если лучше на ≥10% и ≥5 мс, чтобы не было дребезга.
- Прямой живой линк всегда в приоритете перед ретрансляцией с близкой стоимостью.
- `FORWARD` со счётчиком хопов (`limit`/`hops`, §6.4) — защита от петель во время сходимости и основа traceroute.
- Результат публикуется через `ArcSwap<RouteSnapshot>` — горячий путь пакетов не берёт блокировок.

### 6.3. Установление соседства

Источники кандидатов в соседи:

1. трекер: `Found` для онлайн-участников той же группы (без взаимного Search);
2. статические пиры из конфига (§10);
3. `endpoints` из LSA других узлов (работает при недоступном трекере);
4. локальные адреса-кандидаты (адреса интерфейсов + порт сокета), которые узел сообщает трекеру и в LSA, — замена multicast-обнаружения в LAN без второго сокета.

Политика: пытаться установить прямой линк со всеми участниками группы до `max_direct` (по умолчанию 64); при большем числе — с ближайшими по RTT + с теми, кому идёт трафик (on-demand). Неудачные попытки — с экспоненциальной паузой.

**Hole punching и типы NAT при одном сокете.** Birthday-атака EasyTier (каждая сторона шлёт с многих портов, чтобы совпасть по парадоксу дней рождения) требует множества сокетов — DVPN так не может. Что доступно с одним сокетом:

- **Тип NAT узел определяет сам**, сравнив, какой внешний порт ему приписали два разных трекера (full-cone / restricted / port-restricted / symmetric), и публикует его в LSA (поле `nat_type`, как в `RoutePeerInfo` EasyTier).
- **Full/restricted cone ↔ любой:** обычный punch — обе стороны одновременно шлют друг другу (трекер сводит их через `Punch`/`Found`), мэппинги открываются. Это основной путь, он работает с одного сокета.
- **Symmetric ↔ cone:** конусная сторона предсказуема; symmetric-сторона шлёт, cone-сторона отвечает на наблюдаемый адрес. Работает.
- **Symmetric ↔ symmetric:** оба порта непредсказуемы. С одним сокетом надёжно не пробивается — узел **предсказывает** несколько следующих портов соседа (по шагу, замеченному на двух трекерах) и шлёт на небольшой диапазон (десятки портов) — дёшево с одного сокета, иногда срабатывает. Если нет — честный откат на **relay** (§4.3/§11), связь есть в любом случае.
- `persistent_keepalive` (§10) удерживает открытый мэппинг, чтобы линк не закрывался по таймауту NAT.

### 6.4. TTL и traceroute

В Yggdrasil-ng CKR транзитный узел не трогает TTL, поэтому traceroute не видит промежуточных узлов, а петли не гасятся TTL. В DVPN ретранслятор ведёт себя как обычный маршрутизатор. Сложность в том, что ретранслятор не видит IP-заголовок (он зашифрован сквозной сессией), поэтому TTL переносится в заголовок `FORWARD`, который ретранслятор расшифровывает:

1. **Источник** (узел, где пакет вышел из TUN) ставит `limit = min(IP TTL / Hop Limit, MAX_HOPS=16)`, `hops = 0`. Если `IP TTL ≤ MAX_HOPS`, источник присваивает пакету `probe` (16 бит, ≠ 0) и кладёт в кольцевой буфер (≈256 записей) копию IP-заголовка + 8 байт — то, что нужно процитировать в ICMP. Обычный трафик (TTL 64/128) идёт с `probe = 0`, без затрат.
2. **Ретранслятор**: `hops += 1`; если `hops >= limit` — пакет не пересылается. При `probe ≠ 0` ретранслятор отправляет источнику `ICMP_REPORT {probe, reporter = свой ключ, code = time_exceeded}` (с ограничением частоты); при `probe = 0` (петля при большом TTL) — молча отбрасывает.
3. **Источник** по `ICMP_REPORT` достаёт заголовок из буфера и пишет в TUN ICMP Time Exceeded (IPv4 type 11 / ICMPv6 type 3) **от overlay-адреса ретранслятора** (его IPv4 в группе или ULA для IPv6; если подходящего адреса нет — ответа нет, traceroute покажет `*`).
4. **Получатель** перед записью в TUN уменьшает TTL на `hops` (для IPv4 — инкрементальный пересчёт контрольной суммы, RFC 1624).

Ядро на шлюзах и конечных узлах уменьшает TTL само (обычный forwarding), так что `traceroute` из LAN за узлом A до LAN за узлом C через B покажет: шлюз A → B → C → хост. Для прямого линка промежуточных хопов нет, как в WireGuard.

Там же источник генерирует ICMP Destination Unreachable, если для адреса нет маршрута или узел недоступен, и Fragmentation Needed / Packet Too Big, если пакет не влезает в MTU текущего пути (с учётом накладных расходов relay).

## 7. CKR: маршрутизация подсетей по ключам

### 7.1. Таблица

`CkrTable`: LPM-таблица `IpNet → NodeId` для IPv4 и IPv6 (crate `prefix-trie` или своя, как `RouteTable` в `Yggdrasil-ng/crates/yggdrasil/src/ckr.rs`). Источники:

1. **автоматически** из состояния группы: адреса узлов (`/32`, `/128`) + их `routes` (подсети за узлом), §8;
2. **вручную** в `config.toml` (как `remote_subnets` в Yggdrasil) — перекрывает автоматическое.

Синтаксис записей (совместим с Yggdrasil CKR):

| Запись | Смысл |
|---|---|
| `10.0.0.0/24`, `fd00::/64`, `10.0.0.5` | маршрут + системный маршрут (адрес без маски = /32 или /128) |
| `~10.0.0.0/8` | только CKR, системный маршрут не ставится |
| `!192.168.1.0/24` | исключение из диапазонов этого узла |
| `inetv4` / `~inetv4` | все публичные IPv4 (без приватных) |
| `inetv6` / `~inetv6` | `2000::/3` |

### 7.2. Путь пакета

**TUN → сеть:** `dst IP → CkrTable (LPM) → NodeId → RouteSnapshot.next_hop → link-сессия` (прямо или `FORWARD`).

**Сеть → TUN:** источник пакета должен попадать в префиксы, принадлежащие **отправителю** (по сквозной сессии, а не по UDP-адресу). Это обобщение текущей проверки `payload[12..16] == peer.addr` и правило CKR «трафик из интернета принимается, если он пришёл от exit-узла».

### 7.3. Системные маршруты и underlay

- Linux: `rtnetlink` (или на первом этапе вызовы `ip route`, как в yggmgr), Windows: IP Helper API / `route`, macOS: `route`.
- Ставятся при старте и при изменении плана, снимаются при выходе; только «свои» маршруты (помечать `proto`/metric).
- **Underlay-исключения (как в yggmgr):** если маршрут покрывает адрес трекера, статического пира или endpoint соседа — для него ставится `~` (без системного маршрута) или исключение `!ip/32`, иначе трафик самого DVPN уйдёт в туннель.
- Конфликт префиксов (один префикс у двух узлов) отклоняется при записи в состояние; при гонке побеждает правило детерминированно (старшая запись, затем меньший ключ), второй — предупреждение в логе/API.

### 7.4. ACL внутри группы

Сейчас (v3) любой узел может достучаться до любого адреса и порта любого другого. Нужен контроль доступа, как ACL-группы в EasyTier и `[firewall]` в Yggdrasil.

- Входящий из сети пакет перед записью в TUN проверяется по правилам группы: `(источник-тег → назначение-тег, протокол, порты) → allow/deny`, default-deny или default-allow задаётся в `Settings`.
- **Теги** узлов — в сертификате (`roles`/`tags`), поэтому их нельзя подделать: отправитель известен по сквозной сессии (§4.3), а его теги подписаны админом.
- Правила — в `Settings` группы (реплицируются как часть состояния), применяются одинаково всеми узлами; проверка — на стороне получателя (и, по желанию, на exit-узле для исходящего).
- Реализация: та же LPM-таблица + сопоставление портов; на горячем пути — скомпилированный снимок через `ArcSwap`.
- MVP может выйти с default-allow (поведение как сейчас) и включать ACL позже — но поле в модели заложить сразу.

## 8. Автоматическая синхронизация маршрутов (по образцу yggmgr)

### 8.1. Модель состояния группы

Записи (по образцу `yggmgr/src/model.rs` и `store.rs`):

```rust
enum Body {
    Node(NodeInfo),        // автор — сам узел (или админ)
    Settings(Settings),    // автор — админ
    Revoke(Revoke),        // автор — админ
}

struct NodeInfo {
    name: String,
    key: NodeId,
    addresses: Vec<IpAddr>,        // свои адреса на TUN (IPv4 и/или IPv6)
    routes: Vec<IpNet>,            // подсети за узлом (LAN)
    static_endpoints: Vec<String>, // если узел — статический (host:port)
    gateway_v4: bool,              // даёт выход в IPv4-интернет (forward + NAT)
    v6_prefixes: Vec<Ipv6Net>,     // публичные IPv6-префиксы, раздаваемые через узел
    exit_v4: Vec<NodeId>,          // шлюзы для этого узла по приоритету (failover)
    exit_v4_sources: Vec<Ipv4Net>, // policy routing только для этих источников
    exit_v6: bool,
    relay: bool,                   // разрешает транзит
}

struct Settings { ipv4_pool: Option<Ipv4Net>, ipv6_ula: Option<Ipv6Net>, ipv6_pool: Option<Ipv6Net>, psk_epoch: u32 }
```

Версионирование:

- `Entry { id, ts: HLC (мс), author, deleted, body }`, подпись Ed25519 автора по точным байтам payload (как `SignedRecord` в yggmgr — сохраняет совместимость при добавлении полей);
- LWW: побеждает больший `(ts, author)`; удаления — tombstones;
- записи из будущего дальше `MAX_CLOCK_SKEW` (10 мин) отклоняются;
- кто может писать: запись `node/<key>` — сам узел или админ; `settings`, `revoke/*` — только админ; автор любой записи должен иметь действующий неотозванный сертификат.

### 8.2. Синхронизация

- Прямой обмен (kind 3 по link-сессиям): `Summary [(id, ts, author)]` → недостающие записи в обе стороны; каждые 30 с и сразу после локального изменения.
- Через трекер (§5.4): те же записи в зашифрованном виде.
- Состояние хранится в `state.json` (подписанные записи, перепроверяются при загрузке) — заменяет `peers.json`.

### 8.3. Plan / Apply

Детерминированная функция `plan(view, self_key, chosen_gateway) -> Plan` (аналог `yggmgr/src/plan.rs`):

- CKR: адреса и подсети всех остальных участников → их ключи;
- маршруты, покрывающие underlay → `~prefix` / `!ip/32`;
- `exit_v4` → `inetv4` (или `~inetv4` + policy routing по `exit_v4_sources`) через выбранный шлюз;
- `exit_v6` → `inetv6` через узел-владелец IPv6-префикса;
- для шлюза: `ip_forward`, NAT (nftables-таблица `inet dvpn`), MSS clamp, NDP proxy для публичных IPv6;
- адреса TUN = `addresses` своего узла (добавлять/снимать на лету, только «свои»).

`apply_loop` каждые 15 с и по событию: сравнить план с текущим и применить разницу. Отказоустойчивость шлюза: выбор первого живого из `exit_v4` по LSDB/RTT, удержание (`PREEMPT_HOLD`) перед возвратом на приоритетный — как `choose_gateway` в yggmgr.

Важное отличие от yggmgr: yggmgr управляет внешним Yggdrasil через admin-API; в DVPN всё это **внутри одного процесса**, CKR-таблица меняется атомарно через `ArcSwap` без перезапусков.

## 9. IPv6

### 9.1. Underlay (транспорт)

- **Один сокет:** `[::]:port` с `IPV6_V6ONLY=0` (Linux, Windows, macOS, Android). IPv4-пиры видны как `::ffff:a.b.c.d` — нормализовать к IPv4 в хранилище и логах. Где dual-stack недоступен (например OpenBSD), узел работает в одном семействе адресов, выбранном в конфиге (`family = "v4" | "v6" | "dual"`); второго сокета нет. `change_port` по-прежнему меняет единственный сокет.
- Трекер: `Announce` содержит локальные кандидаты (адреса интерфейсов + порт), трекер добавляет наблюдаемые v4/v6; `Found` возвращает **список** endpoint-ов.
- Подключение: параллельные попытки по всем кандидатам (happy eyeballs: IPv6 первым, IPv4 через 50–100 мс); линк выбирает лучший живой путь, остальные — резерв.
- `ServerConfig`: убрать `find(SocketAddr::is_ipv4)`, хранить все резолвы, переразрешать DNS периодически.

### 9.2. Overlay (TUN)

- Разбор пакетов вынести в `packet.rs`: версия, src/dst для IPv4 (`12..16`, `16..20`) и IPv6 (`8..24`, `24..40`).
- Адреса TUN: несколько адресов (v4 и v6) через `tun-rs` (`add_address_v6` — проверить поддержку на всех ОС).
- **ULA, выведенный из ключа:** `fdXX:XXXX:XXXX::/48` из `HKDF(group_id)` (RFC 4193 global id) + 80 бит из `hash(node_key)`. Адрес детерминирован, распределять его не нужно, коллизии практически исключены, подделать источник нельзя (проверка `src == ula(sender)`). Это аналог `200::/7` в Yggdrasil, но приватный для группы.
- MTU: при IPv6 overlay минимальный MTU 1280; посчитать накладные расходы (прямой путь ~30 байт + UDP/IP; через relay ~+80) и при превышении отвечать ICMP Fragmentation Needed / ICMPv6 Packet Too Big; опционально MSS clamp на TUN.

## 10. Статические соединения

```toml
[[static_peers]]
key = "XB4p...base64url"                    # обязателен: без ключа нет handshake IK
endpoints = ["203.0.113.10:8647", "vpn.example.com:8647", "[2001:db8::10]:8647"]
group = "home"                             # какой psk использовать
persistent_keepalive = 25                  # секунды, для удержания NAT
```

- Узел сам инициирует handshake к статическим пирам без трекера, переразрешает DNS, повторяет с экспоненциальной паузой (1 с → 60 с).
- Узел со статическим адресом настраивает фиксированный `bind_port` (не диапазон) и публикует `static_endpoints` в своей записи — остальные участники группы узнают его из состояния автоматически.
- Статический узел с `relay = true` — естественный «опорный» узел сети (аналог публичного узла EasyTier / пира Yggdrasil): работает даже без трекера.
- Входящие соединения от неизвестных ключей принимаются, если handshake прошёл с psk группы (и при этапе B — с валидным сертификатом).

## 11. Трекер v4

```rust
enum TrackerMsg {
    // клиент → сервер
    Announce { node: NodeId, groups: Vec<GroupId>, candidates: Vec<SocketAddr>, certs: Vec<MemberCert>, sig },
    StateSummary { group: GroupId, summary: Vec<(RecordIdHash, u64)> },
    StatePut { group: GroupId, records: Vec<EncryptedRecord> },
    StateGet { group: GroupId, ids: Vec<RecordIdHash> },
    Punch { target: NodeId },                 // «хочу прямой линк» — сервер уведомит обе стороны
    // сервер → клиент
    Found { node: NodeId, endpoints: Vec<SocketAddr> },
    State { group: GroupId, records: Vec<EncryptedRecord> },
    Close,
}
```

- `sig` в `Announce` — подпись ключом узла над транскриптом handshake с трекером (`client_eph|nonce|server_eph`): владение ключом доказано, угнать чужой endpoint нельзя.
- Членство: трекер проверяет `MemberCert` подписью `group_id` и список отзывов; узел без действующего сертификата не попадает в индекс группы.
- Сервер сам рассылает `Found` всем онлайн-участникам группы при появлении нового (без взаимного Search).
- Несколько трекеров: каждый — независимая реплика; узел держит сессии со всеми.
- **Relay через трекер (опционально, этап 8):** пересылка `DATA` между двумя узлами через тот же сокет трекера, если между ними нет ни прямого пути, ни пути через участников; с лимитом скорости на группу. Трекер видит только зашифрованные пакеты.
- Трекер видит `group_id` и ключи участников (принятое решение) — это позволяет ему проверять подписи `Announce` и сертификаты членства.
- Трекер тоже работает на одном dual-stack сокете.

### 11.1. Маскировка трафика с трекером

Из-за единственного сокета (§«Принятые решения») трафик к трекеру идёт с того же порта, что и трафик к пирам. Если handshake с трекером оставить открытым (как в v3: первый байт `0x01`, HELLO ровно 128 байт, ответ на любой HELLO) — DPI вычислит трекер по сигнатуре, а за ним и всех, кто с ним говорит. Поэтому **сессия с трекером маскируется так же, как p2p**:

- ключ защиты заголовка и профиль для трекера выводятся из его **публичного ключа** (он известен из конфига/invite): `HKDF(tracker_pub, "dvpn/4 tracker obfs")`. Профиль группы здесь не подходит — трекер обслуживает много групп и не знает заранее, кто к нему идёт;
- узел кодирует эфемерный ключ Elligator2 так же, как в p2p-handshake;
- **защита от активного зондирования:** трекер отвечает на `HELLO` только если снятый payload содержит валидный свежий timestamp (TAI64N) в пределах окна и этот (эфемерный ключ, nonce) ещё не встречался. Повтор перехваченного `HELLO` → нет ответа, зонд не отличает трекер от «молчащего» UDP-порта;
- принцип «ответ не больше запроса» (нет амплификации) сохраняется.

### 11.2. Ограничения ретрансляции

Чтобы один участник не загрузил чужой узел-ретранслятор (своим транзитом или транзитом через трекер):

- лимит скорости и объёма на соседа по каждому направлению транзита (token bucket);
- при перегрузке — честное разделение: транзит с наименьшим приоритетом отбрасывается первым, свой трафик узла и управляющие пакеты (LSA/STATE/control) не страдают;
- `relay`-роль в сертификате (§5.2) — только узлы с ней ретранслируют; остальные `FORWARD` отвергают;
- (не критично для MVP, можно во вторую очередь.)

## 14a. Дополнительные подсистемы

### DNS внутри сети (MagicDNS)

Чтобы обращаться к узлу по имени, а не по адресу. Имена уже есть в состоянии группы (`NodeInfo.name`).

- Встроенный DNS-резолвер слушает на overlay-адресе узла (напр. `10.x.x.x:53` и ULA), отвечает на зону вида `<name>.<group>.dvpn` → адреса узла из состояния; остальное — форвард на апстрим (или блок).
- Применение: на Linux — запись в `systemd-resolved`/`resolv.conf` для зоны; где нельзя — узел печатает инструкцию.
- Как MagicDNS в EasyTier; опционально (`[net] magic_dns = true`).

### Exit-узлы: утечки и kill switch

- При `exit_v4`/`exit_v6` DNS-запросы клиента должны идти **через туннель** (иначе провайдер видит имена) — резолвер перенаправляется на DNS внутри сети или на заданный через туннель.
- **Kill switch** (`[net] kill_switch = true`): пока выбранный exit-шлюз недоступен, исходящий трафик по соответствующим маршрутам блокируется (а не утекает напрямую). На Linux — правило в той же nftables-таблице `inet dvpn`.
- Underlay-исключения (§7.3) гарантируют, что сам трафик DVPN не попадёт под kill switch и не уйдёт в туннель.

### Бэкап ключей и права на файлы

- Приватный ключ узла и секрет группы (у админов) лежат в `config.toml` → права **`0600`**, на Windows — ACL только владельцу; при старте узел предупреждает, если права шире.
- `dvpn group backup --out file` — экспорт `group_secret` и админ-материала, зашифрованный паролем (scrypt/argon2 + XChaCha20). Потеря всех админов означает, что группу нельзя расширять и продлевать сертификаты, поэтому бэкап и ≥2 админа — обязательная рекомендация в README.
- `dvpn group restore` — восстановление на новом узле-админе.

### Часы без RTC (роутеры, embedded)

Срок сертификатов (`not_after`) и HLC зависят от времени, а на роутере до синхронизации NTP часы могут показывать 1970 год.

- При старте, пока время заведомо неверно (меньше даты сборки), узел **не отвергает** сертификаты по `not_after` и помечает HLC как «непроверенный», работая по монотонным часам;
- после скачка времени (NTP) — пересчёт; записи из «будущего» в пределах `MAX_CLOCK_SKEW` (§8.1) принимаются.
- Это предотвращает ситуацию «узел с нулевыми часами считает все сертификаты просроченными и не поднимает сеть».

### Диагностика и наблюдаемость

- `dvpn ping <узел>` — RTT до узла (overlay ping по control-пакету, не ICMP).
- `dvpn path <узел>` — путь по mesh из LSDB (список хопов + стоимость); дополняет сетевой `traceroute` (§6.4).
- `dvpn neighbors` / `dvpn routes` — линки (endpoint, RTT, потери, повторные handshake, объём) и CKR-таблица с next hop.
- Счётчики на линк и на сессию; опционально экспорт в Prometheus (`[app] metrics_addr`).

### Fuzzing и property-тесты

Все разборщики принимают данные из сети — обязателен `cargo-fuzz`:

- цели: `obfs` (снятие маски), разбор handshake, `packet.rs` (IP-заголовки), разбор записей состояния и LSA, msgpack API.
- property-тесты (`proptest`): LWW-слияние сходится независимо от порядка доставки; Dijkstra/`next_hop` не образует петель; CKR LPM = эталонный линейный поиск.
- фаззинг-цели — часть CI.

## 15. Этапы внедрения

Каждый этап — рабочая сборка с тестами. Протокол v4 несовместим с v3: сеть переводится целиком (это нужно явно указать в README).

### Этап 0. Подготовка (без изменения поведения)
- `packet.rs` (разбор IPv4/IPv6), `ArcSwap`-снимок маршрутов вместо `RwLock` на горячем пути.
- Интеграционный тест в network namespaces (по образцу `yggmgr/tests/netns-e2e.sh`): трекер + 3–4 узла, NAT через `iptables MASQUERADE`, проверка ping/iperf.
- Каркас `cargo-fuzz` и `proptest` в CI (§14a) — цели добавляются по мере появления разборщиков.
- **Готово, когда:** текущие тесты и netns-тест проходят, фаззинг-каркас собирается в CI.

### Этап 1. Идентичность по ключу
- `NodeId`, `Identity`, ключ в конфиге, base64url в CLI/API/логах.
- Трекер: `Announce` с подписью ключом узла.
- **Готово, когда:** нельзя анонсировать чужой ключ (тест), CLI/API работают с ключами.

### Этап 2. Noise-сессии, шифрование обязательно, маскировка
- `noise.rs`, `link.rs`, wire-формат §4.2, receiver_idx, роуминг по аутентифицированным пакетам, rekey.
- `obfs.rs` (§4.4): Elligator2, защита заголовка, случайный паддинг, случайные тайминги — базовая маскировка всегда включена; junk/signature-пакеты и настраиваемый профиль.
- Удалить `PLAIN`, `PeerCipher`, поле `key` у пиров.
- Пока psk, сертификат и профиль маскировки задаются вручную в конфиге (полноценные группы — этап 3).
- **Готово, когда:** узел без psk/ключа не устанавливает сессию; смена NAT-порта не рвёт связь; в дампе трафика нет постоянных байт/размеров (тест: энтропия заголовка, гистограмма размеров); повтор перехваченного handshake не даёт ответа; бенчмарк не хуже v3 (`bench_peer_cipher` → новый).

### Этап 3. Группы с сертификатами, трекер v4, статические пиры, IPv6 underlay
- `group.rs` (create/invite/join), несколько групп, psk по группе; профиль маскировки `[groups.obfs]` входит в invite и применяется всеми участниками.
- `MemberCert`, роли, `allowed_prefixes`, админы, отзыв, эпохи psk, продление сертификатов; проверка сертификата в handshake и на трекере. Окно перехода для psk/профиля (§4.4).
- Трекер: индекс групп, `Found` без взаимного Search, списки endpoint-ов; **маскировка трекер-сессии и защита от зондирования (§11.1)**.
- `[[static_peers]]`, фиксированный порт.
- Dual-stack транспорт на одном сокете, happy eyeballs.
- Бэкап/восстановление админ-ключей (`dvpn group backup/restore`), права `0600` на ключи, работа при неверных часах до NTP (§14a).
- **Готово, когда:** новый узел входит в сеть по invite без ручного обмена; два узла соединяются только по статическому адресу без трекера; связь по чистому IPv6; исключённый (отозванный) узел не может установить сессию и не виден в индексе трекера; трекер не отвечает на повтор перехваченного handshake; узел с часами «1970» поднимает сеть после NTP.

### Этап 4. IPv6 overlay + CKR (ручная таблица)
- `ckr.rs` (LPM, синтаксис Yggdrasil), несколько адресов на TUN, auto-ULA.
- Проверка источника по префиксам отправителя.
- Системные маршруты (Linux сначала, затем Windows/macOS), underlay-исключения.
- **Готово, когда:** site-to-site (две LAN за узлами) и exit-узел (`0.0.0.0/1`+`128.0.0.0/1`) работают в netns-тесте.

### Этап 5. Mesh-маршрутизация
- LSA, LSDB, синхронизация, Dijkstra, `FORWARD`, e2e-сессии через relay, on-demand прямые линки, гистерезис.
- TTL/Hop Limit через ретрансляторы, `ICMP_REPORT`, генерация Time Exceeded / Unreachable / Packet Too Big (§6.4).
- **Готово, когда:** в netns-топологии A–B–C (A и C не видят друг друга) A↔C работает через B; `traceroute` и `traceroute6` от A до C показывают B; при появлении прямого пути трафик переходит на него; при падении B — на другой relay.

### Этап 6. Реплицируемое состояние и автоматические маршруты
- `state/`, синхронизация напрямую и через трекер (зашифрованно), `plan.rs`, apply-цикл, NAT/forwarding для шлюзов, failover `exit_v4`, NDP proxy.
- ACL группы (§7.4), MagicDNS (§14a), kill switch и защита от DNS-утечек на exit-клиентах (§14a).
- `state.json` вместо `peers.json`; CLI через API демона; диагностика `dvpn ping/path/neighbors/routes`, счётчики (§14a).
- **Готово, когда:** добавление подсети на одном узле за ≤30 с появляется в маршрутах всех; работа без трекера (только p2p-gossip); падение шлюза → переключение; правило ACL deny блокирует доступ (тест); при недоступном exit трафик не утекает мимо туннеля.

### Этап 7. Android и мобильные клиенты
- Защита единственного сокета через `VpnService.protect()` (иначе трафик DVPN уйдёт в собственный туннель); UniFFI-биндинги (как в Yggdrasil-ng); экономный к батарее keepalive; импорт группы по QR.
- Режим `Static`-клиента для устройств без фонового демона.
- **Готово, когда:** Android-узел входит в группу по QR и держит связь в фоне без утечки собственного трафика в туннель.

### Этап 8. Дополнительно
- Relay через трекер (тот же сокет), cookie-защита handshake от DoS, лимиты ретрансляции (§11.2), экспорт метрик Prometheus.
- Не делаем: TCP/WebSocket-транспорт и multicast-обнаружение — они требуют дополнительных сокетов.

## 16. Что стоит переделать и сделать лучше (предложения)

1. **Модель шифрования «ключ получателя» — принципиальная уязвимость.** Кто знает ключ X, может подделать пакеты от любого отправителя к X и читать всё, что шлют X. Переход на Noise с ключами узлов — не косметика, а исправление безопасности. Стоит сделать в первую очередь, даже без mesh.
2. **Угон peer_id на трекере.** Сейчас трекер принимает `Announce` с любым id. До перехода на ключи можно хотя бы предупредить в README.
3. **Отправитель по UDP-адресу** → индекс сессии (WireGuard). Убирает трюк с роумингом и попытки расшифровки пакетов с неизвестных адресов (это ещё и CPU-DoS вектор).
4. **Разделить быстрое и медленное состояние:** LSA (RTT, соседи — секунды) отдельно от конфигурации (адреса, подсети — дни). В EasyTier всё в одном `RoutePeerInfo`, и это усложняет код (6.5k строк в `peer_ospf_route.rs`).
5. **Трекер как зашифрованная реплика**, а не только rendezvous: сеть переживает недоступность трекера, а сервер не узнаёт состав сети и маршруты (в отличие от централизованного режима EasyTier).
6. **Горячий путь:** сейчас `tun_loop` делает `RwLock::read` + clone `Route` (с `PeerCipher`) на каждый пакет и `await` на каждой отправке. Лучше: `ArcSwap`-снимок, пакетная отправка (`sendmmsg`/GSO на Linux), отдельные задачи шифрования при высокой нагрузке.
7. **CLI через API демона**, а не прямая правка файлов при работающем узле — иначе гонки записи `peers.json`/`state.json`.
8. **Адрес из ключа (auto-ULA)** вместо ручного распределения адресов — меньше ручной работы, невозможность подделать источник по IPv6. IPv4 оставить из пула (`ipv4_pool`) с детерминированным выбором и проверкой конфликтов.
9. **Один процесс вместо связки «VPN + менеджер»:** то, что в yggmgr делается внешним менеджером через admin-API и nftables, в DVPN лучше встроить — меньше движущихся частей, атомарные изменения таблиц.
10. **Тесты в network namespaces** как обязательная часть CI — у mesh/NAT-логики много краевых случаев, которые юнит-тестами не ловятся.
11. **Traceroute как инструмент отладки mesh:** в Yggdrasil-ng CKR транзит не уменьшает TTL, и путь через сеть невидим. В DVPN TTL уменьшается на каждом ретрансляторе (§6.4) — сразу видно, через какие узлы идёт трафик и где он теряется. Синтаксис CKR оставлен таким же, как в Yggdrasil, чтобы опыт и конфиги переносились.
12. **Версионирование протокола:** байт версии/возможностей в handshake с самого начала v4, чтобы следующие изменения не ломали сеть целиком, как переход v3 → v4.
13. **Маскировка от DPI с самого начала (§4.4):** v3 имел явный отпечаток (фиксированный первый байт, размеры HELLO 128/97). В v4 маскировка — часть wire-формата, а не надстройка, поэтому её нельзя забыть «включить». Профиль группы версионируется, чтобы менять сигнатуру, если её начали блокировать.

## 17. Риски

| Риск | Мера |
|---|---|
| Петли и дребезг маршрутов при сходимости | TTL в FORWARD, двусторонняя проверка рёбер, гистерезис |
| MTU/фрагментация через relay | расчёт overhead, ICMP PTB/Frag Needed, MSS clamp |
| Маршрут на underlay уводит DVPN в туннель | автоматические `~`/`!` для трекеров, статических пиров, endpoint-ов |
| Сдвиг часов ломает LWW | HLC, `MAX_CLOCK_SKEW`, отклонение записей из будущего |
| DoS на handshake | rate limit, cookie (этап 8), mac1 с ключом получателя |
| Утечка `group_secret` | секрет только у админов, участники держат сертификат; ротация psk по эпохам |
| Потеря всех админов → группа замирает | `dvpn group backup`, рекомендация ≥2 админа |
| Смена профиля/psk раскалывает сеть | окно перехода: оба профиля/psk принимаются одновременно (§4.4) |
| Трекер виден по единому сокету | маскировка трекер-сессии, отсутствие ответа на зонд (§11.1) |
| DNS-утечка на exit-клиенте | DNS через туннель + kill switch (§14a) |
| Часы «1970» на роутере отвергают сертификаты | работа по монотонным часам до NTP, затем пересчёт (§14a) |
| Elligator2 реализован неверно → сигнатура | тестовые векторы obfs4/arti, случайные старшие биты, отдельный crate/аудит (§4.1) |
| Маскировка добавляет overhead/задержку | умеренный профиль по умолчанию, агрессивный — только где нужно; паддинг не превышает MTU |
| Сигнатуру профиля начали блокировать | профиль версионируется и меняется через invite/состояние без смены протокола |
| Объём работ | этапы независимо полезны: 1–2 уже закрывают проблемы безопасности v3 |
