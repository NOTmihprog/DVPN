# Как это устроено

[← к содержанию](../README.md#документация)

## Общая картина

```
   узел A (за NAT)                 сервер обнаружения                узел B (за NAT)
  ┌───────────────┐    announce     ┌─────────────┐    announce     ┌───────────────┐
  │ TUN 10.10.33.2│ ──────────────► │ dvpn server │ ◄────────────── │ TUN 10.10.33.3│
  │     dvpn      │ ◄── адрес B ─── │  UDP 6485   │ ─── адрес A ──► │     dvpn      │
  └──────┬────────┘                 └─────────────┘                 └───────┬───────┘
         │                                                                  │
         └──── прямой UDP-туннель (hole punching), Noise IKpsk2 + маскировка ┘
                                      │
                        если прямой путь невозможен:
                     A ──► ретранслятор R ──► B (сквозная сессия A↔B)
```

**Узел** — процесс `dvpn` на машине участника. У него:

* **ключ узла** (Ed25519) — его идентичность; публичный ключ (43 символа base64url) и есть id узла;
* **один UDP-сокет** для всего: серверы обнаружения, прямые соседи, ретрансляция;
* **TUN-интерфейс** (`dnet`) с адресами в сети группы — IPv4 из сертификата и IPv6 из ULA группы;
* **локальный API** для команд управления, GUI и своих программ.

**Группа** — сеть участников. Её id — публичный ключ группы; секрет группы хранится у админа и подписывает
сертификаты участников и записи группы. Подробно — [groups.md](groups.md).

**Сервер обнаружения** (трекер) знакомит узлы одной группы: сообщает им внешние адреса друг друга. Трафик
через него не идёт. Подробно — [discovery.md](discovery.md).

## Жизненный цикл соединения

1. Узел подключается к серверам обнаружения. Сессия с сервером устроена так же, как между узлами (Noise IKpsk2 и
   маскировка), ключи маскировки выводятся из публичного ключа сервера.
2. Узел сообщает серверу свой сертификат и адреса своих интерфейсов (announce). Сервер проверяет сертификат по
   id группы и держит список участников, которые сейчас в сети.
3. Сервер сообщает узлу участников его группы (сертификаты и адреса: тот, что видит сам сервер, плюс адреса
   интерфейсов участника), а им — о новом узле. Узел сам перепроверяет каждый сертификат.
4. Узлы одновременно шлют друг другу рукопожатия Noise на все известные адреса — это пробивает NAT (UDP hole
   punching). Побеждает первый ответивший адрес. Рукопожатие проходит, только если у обоих psk группы и
   действующий сертификат.
5. После рукопожатия — keepalive раз в 12–18 с с замером RTT; смена ключей каждые ~2 минуты. Если сосед молчит
   45 с, связь считается потерянной и поиск начинается заново.
6. Пакет сессии с нового адреса (NAT сменил порт, ноутбук сменил сеть) переводит сессию на этот адрес (roaming).
   Решение принимается только по аутентифицированным пакетам.
7. Пока прямого пути нет, трафик идёт через ретрансляторы ([mesh.md](mesh.md)), а узлы продолжают пробивать
   прямой путь.

Если сервер обнаружения недоступен, установленные соединения продолжают работать, а записи группы
(сертификаты, отзывы, маршруты) расходятся между соседями напрямую.

## Путь IP-пакета

```
приложение → TUN → dvpn: таблица CKR (адрес/подсеть → узел)
                     ├─ есть прямая сессия → DATA по ней → UDP → сосед → его TUN
                     └─ нет → сквозная сессия с узлом → FORWARD → первый ретранслятор → … → узел
```

* **CKR** ([routing.md](routing.md)) по адресу назначения выбирает узел: сам адресат, узел с подсетью
  (site-to-site) или шлюз в интернет ([exit.md](exit.md)).
* На приёме узел проверяет **источник** пакета: он должен маршрутизироваться обратно к соседу, от которого пакет
  пришёл. Узел не может вставить в сеть пакеты с чужих адресов.
* Внутри каждого узла применяются [ACL](acl.md) (nftables), на шлюзе — NAT.

## Протокол на проводе

Все пакеты замаскированы ([obfuscation.md](obfuscation.md)): заголовок зашифрован ChaCha20 ключом группы, к
каждому пакету добавлено случайное заполнение. Логически пакеты такие:

```
HS_INIT  [тип][длина заполнения u16][индекс отправителя u32][сообщение Noise 1]
HS_RESP  [тип][длина заполнения u16][индекс отправителя u32][индекс получателя u32][сообщение Noise 2]
DATA     [тип][длина заполнения u16][индекс получателя u32][счётчик u64][AEAD([вид][тело])][тег 16]
```

Индексы сессий случайные: получатель находит сессию по индексу, адрес отправителя в аутентификации не участвует.
Заголовок DATA — связанные данные AEAD, его подмена ломает проверку.

Вид (`kind`) внутри DATA:

| Вид | Что |
|---|---|
| 0 CONTROL | ping/pong: keepalive, замер RTT, `dvpn ping` |
| 1 IP | IP-пакет для TUN |
| 2 STATE | записи группы (синхронизация между соседями) |
| 3 ROUTING | анонсы связей (LSA) для mesh |
| 4 FORWARD | пакет для другого узла через ретранслятор: `[лимит хопов][хопы][проба][кому 8][от кого 8][пакет сквозной сессии]` |
| 5 REPORT | ретранслятор сообщает источнику об исчерпании хопов или отсутствии пути (traceroute) |
| 32–255 | данные клиентов API ([api.md](api.md#свои-данные-поверх-сети)) |

## Размеры

UDP-датаграмма никогда не больше 1452 байт (1500 − IPv6 40 − UDP 8), поэтому не фрагментируется:

| Путь | Накладные расходы | Наибольший IP-пакет |
|---|---|---|
| прямая сессия | заголовок 15 + вид 1 + тег 16 | 1420 |
| через ретрансляторы | ещё FORWARD 20 + сквозная сессия 32 | 1368 |

По умолчанию MTU туннеля 1350 — пакет влезает в любой путь, а оставшееся место занимает случайное заполнение.
Если поднять MTU, слишком большие пакеты получат ICMP «packet too big» с MTU пути ([mesh.md](mesh.md#icmp-и-mtu)).

## Модули

| Модуль | Что делает |
|---|---|
| `node.rs` | ядро узла: сессии, циклы UDP и TUN, пересылка, синхронизация, задачи по таймерам |
| `noise.rs`, `link.rs` | Noise IKpsk2, сессии с соседями, смена ключей, окно повторов (`replay.rs`) |
| `obfs.rs`, `elligator.rs` | маскировка заголовков, заполнение, Elligator2 |
| `group.rs`, `state.rs` | сертификаты, invite, записи группы (LWW), эпохи psk |
| `tracker_client.rs`, `tracker_server.rs`, `tunnel.rs` | сервер обнаружения и сессия с ним |
| `router.rs` | link-state: LSA, LSDB, Дейкстра, защита рассылки |
| `plan.rs`, `apply.rs` | что должно быть на узле (чистое вычисление: адреса, маршруты, ACL, DNS) и применение разницы к системе |
| `ckr.rs`, `sysroute.rs` | таблица маршрутов и системные маршруты |
| `exit.rs`, `gateway.rs` | выбор шлюза, kill switch; NAT и NDP proxy на шлюзе |
| `acl.rs`, `dns.rs` | ACL (nftables); DNS и mDNS |
| `api.rs`, `main.rs` | локальный API и CLI |
| `metrics.rs` | счётчики трафика и отброшенных пакетов |
| `config.rs`, `backup.rs`, `clock.rs` | конфиг, резервная копия админа, проверка часов |

Полный дизайн и обоснование решений — [PLAN.md](../PLAN.md).
