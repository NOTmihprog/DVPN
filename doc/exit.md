# Выход в интернет

[← к содержанию](../README.md#документация)

Участник может отправлять свой интернет-трафик через другой узел сети — **шлюз** (exit node), например VPS.
Решают двое:

* **шлюз** соглашается быть шлюзом: секция [`[gateway]`](#узел-шлюз-gateway) в его конфиге;
* **участник** сам выбирает, через какие шлюзы ходить: [`dvpn exit`](#выбор-шлюза-dvpn-exit). Можно один,
  несколько по приоритету или ни одного (по умолчанию).

Админ здесь ничего не решает: шлюз не навязывается участникам через сертификат.

## Выбор шлюза: dvpn exit

```shell
dvpn exit --v4 vps1,vps2          # IPv4-интернет через vps1, если он недоступен — через vps2
dvpn exit --v6 vps1               # IPv6-интернет (2000::/3) через vps1
dvpn exit --none                  # без шлюза: интернет напрямую, как без DVPN
dvpn exit                         # показать настройки и текущий шлюз
```

Шлюзы указываются именами участников или ключами, через запятую, лучший первым. Команда пишет секцию `[exit]` в
`config.toml`, работающий узел подхватывает изменение за секунду:

```toml
[exit]
v4 = ["vps1", "vps2"]
v6 = ["vps1"]
kill_switch = true
dns = ["1.1.1.1", "9.9.9.9"]
```

### Какой шлюз используется

* Используется **первый живой** шлюз из списка: с прямой связью или с путём через [ретрансляторы](mesh.md).
* Если он пропал, трафик сразу уходит на следующий.
* На вернувшийся более приоритетный шлюз трафик переходит, только когда тот 30 с проработал стабильно: мигающий
  шлюз не гоняет трафик туда-сюда. Шлюз, который при старте просто подключился позже других, берётся сразу.
* Текущий шлюз видно в `dvpn status` (`dvpn exit` показывает настройки).

### Что идёт через шлюз

| Трафик | Куда |
|---|---|
| публичный IPv4 (`inetv4`) | через шлюз |
| частные IPv4 (`10/8`, `172.16/12`, `192.168/16`, `100.64/10`, link-local, multicast) | как раньше: в LAN |
| глобальный IPv6 `2000::/3` (`inetv6`), если задан `--v6` | через шлюз |
| сеть группы, подсети участников | напрямую участникам, как всегда |
| собственный трафик DVPN (серверы обнаружения, соседи) | мимо туннеля (fwmark, см. [routing.md](routing.md#системные-маршруты)) |
| подсети, к которым узел подключён напрямую (LAN) | в LAN |

Системные маршруты для этого узел ставит сам (Linux). На Windows и macOS пока нужно вручную.

## Kill switch

Пока шлюзы заданы, но **ни один не доступен**, интернет блокируется: публичные адреса остаются в туннеле, где их
некому нести, и ничего не утекает мимо него. Приложение сразу получает ICMP «administratively prohibited», а не
ждёт таймаута. Сеть группы и собственный трафик DVPN при этом работают — узел сможет найти шлюз снова.

```shell
dvpn exit --kill-switch off     # без живого шлюза интернет идёт напрямую
dvpn exit --kill-switch on      # по умолчанию
```

Kill switch действует, только когда шлюзы заданы. С `dvpn exit --none` интернет всегда напрямую. Шлюз считается
заданным, даже если узел пока не знает участника с таким именем (сразу после запуска, опечатка в `config.toml`):
тогда интернет тоже блокируется, а не идёт мимо туннеля. Не считается только сам узел.

## Только для части адресов: --sources и --table

Обычно через шлюз идёт весь узел. На сервере так нельзя: ответы sshd и всех его служб ушли бы в туннель. Для
этого случая через шлюз можно пускать только **часть источников**, например клиентов другого VPN за этим сервером:

```shell
dvpn exit --v4 jelgava --sources 10.10.11.0/24      # IPv4 и IPv6 через запятую; --sources none — убрать
```

```toml
[exit]
v4 = ["jelgava"]
v4_sources = ["10.10.11.0/24"]   # адрес без маски = /32 (/128 для v6_sources)
v6_sources = []
table = 445                      # необязательно
```

Маршруты в интернет (`inetv4`/`inetv6` через шлюз, при kill switch — в никуда) ставятся тогда не в таблицу 7347
всего узла, а в **таблицу выхода**, и туда смотрят только источники:

```text
ip rule  priority 7348  from 10.10.11.0/24 lookup 7348     (после правил 7346/7347: маршруты main важнее)
table 7348: default dev dnet, throw <частные диапазоны>
```

Сам узел и всё остальное ходят в интернет напрямую, как без DVPN. Выбор живого шлюза и kill switch работают как
обычно, но только для этих источников. Источники должны быть в сертификате узла (`--route` у invite или
`dvpn node set --add-route`), иначе шлюз отбросит их пакеты как чужие.

**`--table N`** кладёт маршруты в интернет в таблицу `N` вместо 7348. Без `--sources` DVPN **не ставит к ней
правил** — что туда попадёт, решают ваши правила (по fwmark, интерфейсу, источнику):

```shell
ip rule add priority 99 fwmark 0xad9c lookup 445     # ваше правило, например из nftables
dvpn exit --v4 jelgava --table 445                   # --table none — вернуть таблицу DVPN
```

DVPN помечает свои маршруты `proto 73` и удаляет только их, так что ваши маршруты в этой таблице остаются. Свой
`default` в ней держать не нужно: DVPN заменит его своим. Нельзя указывать таблицы 0, 253–255 и 7347.

С `--sources` или `--table` systemd-resolved **не** получает `~.`: DNS самого узла идёт напрямую, как и его
интернет. DNS-сервер узла по-прежнему пересылает имена на `[exit] dns` через шлюз — для тех, кто им пользуется.

## DNS через шлюз

Чтобы DNS-запросы не уходили провайдеру или домашнему роутеру мимо туннеля:

```shell
dvpn exit --dns 1.1.1.1,9.9.9.9     # --dns none — убрать
```

Пока шлюз активен:

* DNS-сервер узла ([dns.md](dns.md)) пересылает все имена, кроме `.dvpn`, на эти серверы — их адреса публичные,
  поэтому запросы идут через туннель и шлюз;
* systemd-resolved отправляет узлу **все** запросы (домен `~.` на интерфейсе туннеля).

Когда шлюза нет, всё возвращается как было. Без systemd-resolved укажите адрес узла DNS-сервером системы вручную.

## Узел-шлюз: [gateway]

На узле, который будет шлюзом (Linux, nftables):

```toml
[gateway]
wan = ["ens3"]              # интерфейсы в интернет: туда маскарадится трафик из туннеля
ndp_proxy = "ens3"          # необязательно: публичные IPv6 участников из префикса этого интерфейса
manage_sysctl = true        # включить пересылку (ip_forward, IPv6 forwarding, proxy_ndp)
```

Что делает шлюз при старте:

1. **sysctl** (если `manage_sysctl`): включает пересылку IPv4 и IPv6; на WAN-интерфейсах сначала ставит
   `accept_ra = 2`, чтобы не потерять свой IPv6-маршрут по умолчанию из RA;
2. **NAT** — таблица `inet dvpn_gw`: трафик из туннеля в WAN маскарадится (IPv4 и IPv6 с ULA-адресов группы,
   которые снаружи не маршрутизируются);
3. **MSS clamping**: TCP MSS подрезается под MTU туннеля в обе стороны, TCP через туннель не фрагментируется;
4. **NDP proxy** (если `ndp_proxy`): см. ниже.

При остановке шлюз убирает таблицу nftables, NDP proxy и маршруты (sysctl остаются как есть). Проброс портов — в
[разделе ниже](#проброс-портов-dvpn-forward).

Проверка на шлюзе: `nft list table inet dvpn_gw`. Если на шлюзе есть свой файрвол, разрешите пересылку из `dnet`
в WAN и обратно для установленных соединений.

Docker ставит политику `FORWARD` в `DROP`, и `accept` в другой таблице её не отменяет. На шлюзе с Docker разрешите
пересылку в цепочке `DOCKER-USER` (интерфейсы — свои):

```shell
iptables -I DOCKER-USER 1 -i dnet -o ens3 -j ACCEPT
iptables -I DOCKER-USER 2 -i ens3 -o dnet -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
```

## Публичный IPv6 участнику

Если у шлюза есть IPv6-префикс (например, `/64` на VPS), участнику можно дать **настоящий публичный IPv6** из
него — как `ndp_proxy_interface` в yggmgr:

```shell
dvpn node set phone --add-route 2a01:db8:4:390::6/128     # админ: адрес из префикса шлюза
dvpn exit --v6 vps1                                       # участник: IPv6-интернет через шлюз
```

* Участник вешает этот адрес на свой TUN и выходит с ним в IPv6-интернет напрямую, без NAT.
* Шлюз отвечает за этот адрес по NDP на интерфейсе `ndp_proxy` (`ip -6 neigh proxy`) и маршрутизирует его в
  туннель (маршрут `/128` в основной таблице).
* Входящие соединения на этот адрес доходят до участника — позаботьтесь о файрволе на его стороне.

## Проброс портов: dvpn forward

Порт на WAN-интерфейсах шлюза можно пробросить участнику, например веб-сервер в домашней сети на порт VPS.
Команды выполняются на самом шлюзе, работающий узел подхватывает изменения за несколько секунд:

```shell
dvpn forward add 8080 server --to-port 80      # 8080 шлюза → порт 80 участника server (tcp)
dvpn forward add 51820 home --proto udp --keep-ip
dvpn forward list
dvpn forward del 8080
```

Правила пишутся в `config.toml` шлюза:

```toml
[[gateway.forward]]
proto = "tcp"          # tcp, udp или both
port = 8080            # порт на шлюзе
to = "server"          # участник: имя или ключ
to_port = 80           # порт участника (по умолчанию тот же)
keep_ip = false        # участник видит адрес клиента
```

Участник указывается по имени или ключу, его адрес берётся из сертификата: после `dvpn node set --addr` правило
переезжает само. Правило к участнику, которого шлюз пока не знает, ждёт, пока тот появится.

**Чей адрес видит участник.** По умолчанию шлюз подменяет адрес клиента своим адресом в группе. Так проброс работает
к любому участнику, но сервис видит адрес шлюза. С `keep_ip` участник видит настоящий адрес клиента. Для этого
участник должен выходить в интернет **через этот шлюз** (`dvpn exit --v4 <шлюз>`), иначе ответ уйдёт другим путём,
а пакеты с чужих адресов узел принимает только от своего шлюза. С `--sources` адрес участника в группе должен
входить в эти источники.

Свои UDP-порты узла (`[peer] bind_port`) не пробрасываются. ACL участника видит такой трафик как трафик от шлюза
(без `keep_ip`), при `default = "deny"` шлюзу нужно разрешающее правило.

### Проброс от админа

Админ может задать правила для другого шлюза, если тот это разрешил:

```toml
[gateway]
wan = ["ens3"]
allow_remote = true    # применять правила, которые для этого узла задаёт админ
```

```shell
dvpn forward add 8443 server --to-port 443 --on vps1    # на узле админа
dvpn forward list --on vps1
dvpn forward del 8443 --on vps1
```

Правила админа — запись группы, она доходит до шлюза за секунды. Собственные правила шлюза важнее: порт, занятый в
`config.toml`, правилом админа не перекрывается. Без `allow_remote` шлюз правила админа показывает
(`dvpn forward list`), но не применяет. Для одного шлюза можно задать около 14 правил.

## Пример: интернет через VPS

На VPS (участник `vps1`, Linux):

```toml
[gateway]
wan = ["ens3"]
```

У участника:

```shell
dvpn exit --v4 vps1 --dns 1.1.1.1
curl -4 ifconfig.me          # покажет адрес VPS
dvpn status                  # exit_v4: vps1
```
