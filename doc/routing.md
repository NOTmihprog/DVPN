# Адреса и маршруты

[← к содержанию](../README.md#документация)

## Адреса узла

У каждого узла на TUN-интерфейсе (`dnet`) есть:

| Адрес | Откуда | Пример |
|---|---|---|
| **IPv4** в сети группы | из сертификата (`-a` при `create`/`invite`, `node set --addr`), маска — `[net] mask` | `10.10.33.2/24` |
| **IPv6 ULA** | выводится из ключа группы и ключа узла: префикс `/48` у группы, адрес у узла | `fd3c:9a1e:47b2:…/48` |
| **публичный IPv6** (необязательно) | `/128` из префикса шлюза в сертификате | `2a01:db8:4:390::6/128` |

ULA-адрес не нужно раздавать и нельзя подделать: он однозначно получается из ключа узла. Его видно в
`ip -6 addr show dnet` и `dvpn status`, а по имени — `phone.dvpn` ([dns.md](dns.md)).

Публичный IPv6 участнику даёт шлюз с NDP proxy — см. [exit.md](exit.md#публичный-ipv6-участнику).

## Таблица маршрутов (CKR)

Каждый узел держит таблицу «адрес или подсеть → узел» (Crypto-Key Routing, как в Yggdrasil) и выбирает по ней,
кому отправить IP-пакет из TUN. Выигрывает самый длинный префикс. Таблица собирается из:

1. **сертификатов** всех участников (кроме исключённых): их IPv4, ULA-адрес и подсети из сертификата;
2. **выбранных шлюзов** ([exit.md](exit.md)): публичный IPv4 (`inetv4`) и IPv6 (`inetv6`) — к текущему шлюзу,
   а при недоступности шлюзов — в «чёрную дыру» (kill switch);
3. **своих маршрутов** из `[ckr.remote_subnets]` — поверх всего остального.

Таблица перестраивается сразу, как только меняется что-то из этого: новый участник, `node set`, отзыв, смена
шлюза, правка конфига.

```shell
dvpn routes        # таблица CKR и маршруты mesh работающего узла
```

## Подсети за узлами (site-to-site)

Узел может обслуживать **подсети** — например, домашнюю LAN, чтобы до неё можно было достучаться из любой точки.
Подсеть, которую узел вправе обслуживать, админ записывает в его сертификат:

```shell
dvpn group create home -n alice --route 192.168.10.0/24      # LAN за узлом админа
dvpn group invite -n office --route 192.168.30.0/24          # LAN за новым узлом
dvpn node set office --add-route 192.168.31.0/24             # ещё одна, у существующего участника
```

Все участники направляют эти подсети соответствующему узлу и ставят системные маршруты. Чтобы хосты LAN
отвечали, на узле с подсетью:

1. включите пересылку: `sysctl -w net.ipv4.ip_forward=1` (и `net.ipv6.conf.all.forwarding=1` для IPv6);
2. хостам LAN нужен маршрут к сети группы (`10.10.33.0/24`) через этот узел — проще всего прописать его на
   роутере LAN. Либо включите на узле маскарадинг трафика из туннеля в LAN, тогда маршрут не нужен:
   `nft add rule ip nat postrouting iifname dnet oifname eth0 masquerade` (с таблицей и цепочкой `nat`).

Подделать подсеть нельзя: узел, которому её не дали, пакеты с адресов из неё отправить не сможет (см.
[проверку источника](#проверка-источника)).

> Для выхода в интернет **не** давайте узлу `0.0.0.0/0` в сертификате: такой маршрут получили бы все участники.
> Шлюз каждый участник выбирает сам — [exit.md](exit.md).

## Свои маршруты: [ckr.remote_subnets]

Узел может добавить маршруты поверх сертификатов, только для себя:

```toml
[ckr.remote_subnets]
"<ключ узла>" = ["192.168.50.0/24", "~10.0.0.0/8", "!192.168.50.128/25"]
```

Синтаксис записи (совместим с CKR в Yggdrasil):

| Запись | Значение |
|---|---|
| `10.0.0.0/24`, `10.0.0.5` | маршрут к узлу и системный маршрут; без маски — `/32` или `/128` |
| `~10.0.0.0/8` | только внутри DVPN, без системного маршрута |
| `!192.168.1.0/24` | исключение: «не через туннель» (дыра в более широком маршруте) |
| `inetv4`, `~inetv4` | публичный IPv4: `0.0.0.0/0` с дырами для частных диапазонов (`10/8`, `172.16/12`, `192.168/16`, `100.64/10`, `169.254/16`, `127/8`, multicast и др.) |
| `inetv6`, `~inetv6` | `2000::/3` (весь глобальный IPv6) |

Зачем это нужно:

* маршрут к подсети, которую узел обслуживает, но которой нет в его сертификате (например, вы сами управляете
  обоими концами). Принимающий узел примет ответы, только если и у него есть обратный маршрут;
* `!` — оставить часть подсети локальной;
* `~` — маршрутизировать внутри DVPN, но системные маршруты поставить по-своему.

Ручные маршруты не проверяются на пересечение с маршрутами из сертификатов: они просто главнее.

## Проверка источника

Пакет от соседа принимается, только если его **источник** маршрутизируется по таблице обратно к этому соседу
(reverse path check). Значит:

* участник отправляет пакеты только со своих адресов и подсетей из сертификата;
* пакеты из интернета принимаются только от шлюза, который вы сами выбрали;
* пакет с чужим источником отбрасывается с сообщением `packet … with foreign source dropped` в логе.

## Системные маршруты

На Linux узел ставит системные маршруты для таблицы сам — так же, как `wg-quick`:

```
ip rule  priority 7346  lookup main suppress_prefixlength 0    (маршруты LAN главнее)
ip rule  priority 7347  not fwmark 0x7347 lookup 7347           (остальное — по таблице DVPN)
таблица 7347: <подсеть> dev dnet,  throw <исключение>
ip rule  priority 7348  from <источник> lookup 7348             (только с [exit] v4_sources, см. exit.md)
```

* Маршруты локальной сети в основной таблице главнее туннеля: подсеть, к которой вы подключены напрямую, в туннель
  не уходит.
* Собственный трафик DVPN (серверы обнаружения, соседи) помечен fwmark `0x7347` и в туннель не попадает — даже
  при маршруте по умолчанию через шлюз. Исключения для адресов серверов не нужны.
* Маршруты применяются разницей, без сброса. Правила и таблица снимаются при остановке (Ctrl+C, SIGTERM) и при
  старте после сбоя.
* `[net] manage_routes = false` — не трогать системные маршруты (поставьте свои).

Все маршруты DVPN помечены `proto 73`. Посмотреть: `ip rule`, `ip route show table 7347`, `ip -6 route show table
7347`, `ip route show table all proto 73`.

На Windows и macOS системные маршруты пока нужно ставить вручную (поддержка Windows — вместе со сборкой релизов).
