# DVPN

> ### Что это вообще такое?
> Этот проект больше всего похож на [P2PVPN](http://www.p2pvpn.org/)
> и представляет собой шлюз, который создает **прямое соединение** до других пиров. <br><br>

> ### Для чего это можно использовать?
> Этот проект в первую очередь создавался для создания локальной сети в которой все участники сети находятся за nat и не имеют ipv6. <br><br>
> Для меня создание этого проекта решило проблемы с подключением к [Sunshine](https://github.com/LizardByte/Sunshine) на тех ПК которые находятся за nat
> и побочным эффектом стал упавший ping в [cs2](https://store.steampowered.com/app/730/CounterStrike_2/) в тех случаях когда хостом является участник сети, в моем случае ping упал с ~95 на ~30.

> ### Безопасность и анонимность
> DVPN предназначен для частных сетей, участники которых знают друг друга.
> Узел опознаётся по своему **публичному ключу** — его можно показывать кому угодно.
> Секреты — **приватный ключ узла** (`[identity]`) и **ключ сети** (`[group] psk`): кто знает psk и чей ключ есть
> в вашем списке пиров, тот в сети. Не публикуйте их и передавайте только по защищённому каналу. <br>
> Если вашей целью является именно анонимность используйте [Yggdrasil](https://yggdrasil-network.github.io/) + [wireguard](https://www.wireguard.com/) или [i2p](https://geti2p.net/en/), [tor](https://www.torproject.org/).

> [!WARNING]
> **Ветка `DVPN-rs` — версия 4 в разработке.** Протокол v4 **несовместим** с 3.x: узлы v3 и v4 друг друга
> не видят, сеть переводится целиком (см. [Переход с версии 3.x](#переход-с-версии-3x)).
> Формат конфига и CLI ещё будут меняться: ключ сети вместо invite-токенов, `peers.json` и ручная раздача
> списков — временные. План — [PLAN.md](PLAN.md), ход работ — [PROGRESS.md](PROGRESS.md).

## Состояние версии 4

Готово (этапы 0–2 [PROGRESS.md](PROGRESS.md)):

* **идентичность по ключу:** узел — это пара ключей Ed25519, его id — публичный ключ (43 символа base64url);
  подделать чужой id ни перед пирами, ни перед сервером обнаружения нельзя;
* **сессии Noise IKpsk2** (как в WireGuard): взаимная аутентификация по ключам узлов + общий ключ сети,
  прямая секретность, смена ключей каждые ~2 минуты, защита от повторов, переход на новый адрес (roaming) только
  по аутентифицированным пакетам;
* **маскировка:** ни одного постоянного байта и размера на проводе, ключи рукопожатия неотличимы от случайных
  (Elligator2), мусорные и «сигнатурные» пакеты перед рукопожатием — см. [Маскировка трафика](#маскировка-трафика).

Ещё нет (следующие этапы): группы с invite-токенами и сертификатами вместо `[group] psk` и ручной раздачи
списка пиров, статические узлы без сервера обнаружения (`[[static_peers]]`), маскировка трафика к серверу
обнаружения, relay через других участников, выход в интернет через узел сети (exit), IPv6 внутри сети.

## Как это работает

```
   пир A (за NAT)                 сервер обнаружения                 пир B (за NAT)
  ┌───────────────┐ announce/search ┌─────────────┐ announce/search ┌───────────────┐
  │ TUN 10.10.33.2│ ──────────────► │ dvpn server │ ◄────────────── │ TUN 10.10.33.3│
  │     dvpn      │ ◄── адрес B ─── │  UDP 6485   │ ─── адрес A ──► │     dvpn      │
  └──────┬────────┘                 └─────────────┘                 └───────┬───────┘
         │                                                                  │
         └───── прямой UDP-туннель (hole punching), Noise IKpsk2 + маскировка ┘
```

1. Каждый узел открывает **один** UDP-сокет и через него подключается к серверам обнаружения
   (X25519, сервер подтверждает себя подписью Ed25519, дальше сессия ChaCha20-Poly1305).
2. Узел сообщает серверу свой ключ (announce, **подписанный** ключом узла) и просит адреса пиров из своего списка (search).
3. Когда два пира ищут друг друга, сервер одновременно сообщает каждому внешний адрес (IP:порт) другого.
4. Пиры начинают слать друг другу рукопожатия Noise с того же сокета, это пробивает NAT (UDP hole punching).
   Рукопожатие проходит, только если у обоих один и тот же ключ сети и каждый знает ключ другого.
5. После рукопожатия пиры обмениваются keepalive раз в 12–18 с; если пир молчит 45 с, адрес сбрасывается
   и поиск начинается заново. Если пакет сессии пришёл с другого адреса (NAT выдал другой порт, сменилась сеть),
   узел переключается на новый адрес (roaming).
6. IP-пакеты из TUN-интерфейса отправляются напрямую нужному пиру (по его адресу в локальной сети),
   шифруясь ChaCha20-Poly1305 ключами текущей сессии. Сервер обнаружения трафик **не** пропускает через себя.

Сервер нужен только для знакомства пиров. Если он недоступен, уже установленные соединения продолжают работать.

## Сборка

Нужен Rust 1.85+ ([rustup.rs](https://rustup.rs/)).

```shell
git clone https://git.mihprog.com/DVPN/DVPN.git
cd DVPN
git switch DVPN-rs
cargo build --release
# бинарник: target/release/dvpn (dvpn.exe на Windows)
```

### Linux

Для создания TUN-интерфейса нужны права root или capability `CAP_NET_ADMIN`:

```shell
sudo setcap cap_net_admin+ep target/release/dvpn   # чтобы запускать без sudo
```

Без root по умолчанию не получится создать unix-сокет API в `/run/dvpn`, тогда API автоматически
слушает `127.0.0.1:9902` (или укажите свой адрес через `-a`).

### Windows

1. Скачайте [Wintun](https://www.wintun.net/) и положите `wintun.dll` (из папки под вашу архитектуру,
   обычно `bin/amd64`) **рядом с `dvpn.exe`**.
2. Запускайте из консоли **от имени администратора**.
3. Разрешите `dvpn.exe` в брандмауэре Windows (входящий UDP), иначе пиры не смогут достучаться.

Кросс-сборка под Windows с Linux:

```shell
rustup target add x86_64-pc-windows-gnu
cargo build --release --target x86_64-pc-windows-gnu   # нужен mingw-w64
```

## Файлы и каталог данных

| Файл          | Назначение                                                                    |
|---------------|-------------------------------------------------------------------------------|
| `config.toml` | настройки узла: приватный ключ, ключ сети, порты, серверы, TUN, уровень логов |
| `peers.json`  | список пиров сети: ключи, имена, адреса в LAN                                  |

По умолчанию оба файла лежат **рядом с бинарником**. Другой каталог можно задать
опцией `--dir <путь>` или переменной окружения `DVPN_DIR` (действует для всех команд).

При первом запуске любой команды создаётся `config.toml` по умолчанию с новым ключом узла
(секция `[identity]`) и случайным адресом из `10.10.33.0/24`. `config.toml` записывается с правами `0600` —
в нём секреты. Приватный ключ можно не хранить в файле, а передавать переменной окружения `DVPN_PRIVATE_KEY`.

> Свой адрес в LAN хранится в `peers.json` (запись со своим ключом). Если он отличается от `[net] addr`
> в `config.toml`, при запуске значение в `config.toml` будет перезаписано из `peers.json`.

## Пошаговая настройка сети

Пример: сеть из двух участников, Алисы и Боба, и одного сервера обнаружения.

### 1. Сервер обнаружения

На машине с белым IP (VPS) — см. [Запуск сервера обнаружения](#запуск-сервера-обнаружения).
Запомните его **IP, порт и публичный ключ**.

### 2. Организатор: ключ сети

Один раз на всю сеть:

```shell
dvpn gen-key        # → ключ сети (psk), раздать всем участникам по защищённому каналу
```

### 3. Каждый участник: первый запуск, сервер и ключ сети

```shell
dvpn list            # создаст config.toml с ключом узла и покажет себя в таблице
dvpn show-key        # свой публичный ключ — id узла в сети
```

Откройте `config.toml` и добавьте сервер и ключ сети:

```toml
[servers.main]
addr = "203.0.113.10"     # IP или доменное имя сервера
port = 6485
key = "-0-goYUMWn2jfZ2QgYhvS489mWf7G4tgS86dZK18Izo"   # публичный ключ из вывода `dvpn server`

[group]
psk = "..."               # ключ сети из шага 2, одинаковый у всех
```

Серверов можно указать несколько (`[servers.msk]`, `[servers.am]`, …) — узел подключается ко всем.

### 4. Каждый участник: имя и адрес

```shell
dvpn set -p <свой_ключ> -n alice -a 10.10.33.2
```

* `-p` — ключ узла (см. `dvpn show-key` или `dvpn list`). Достаточно однозначного начала ключа: `-p DZVS`.
* `-a` — адрес в виртуальной сети, **уникальный** для каждого участника и из одной подсети (`[net] mask`).

Экспортируйте свою запись и передайте её организатору (в ней только публичный ключ, имя и адрес — не секрет,
но подменённая запись пустит в сеть чужой ключ, поэтому передавайте её так, чтобы организатор был уверен в отправителе):

```shell
dvpn export-peer -o alice.txt
```

### 5. Организатор: собрать общий список

```shell
dvpn import-peer -i alice.txt
dvpn import-peer -i bob.txt
dvpn list
dvpn export -o peers.txt      # общий список всех участников
```

### 6. Каждый участник: импортировать общий список

```shell
dvpn import -i peers.txt      # без -i строку можно вставить в консоль
dvpn list
```

> Узел устанавливает сессию только с теми, чьи ключи есть в его `peers.json`, и только при совпадающем
> `[group] psk`. Новый участник появится у остальных после того, как они импортируют обновлённый список.

### 7. Запуск

```shell
sudo dvpn
```

В логах должно появиться `Connection status connected` (подключение к серверу), затем
`Peer bob(…) new endpoint 1.2.3.4:5678`. Проверка:

```shell
ping 10.10.33.3
```

С `log_level = "DEBUG"` видны рукопожатия (`Link | session with bob(…) established`) и keepalive с замером RTT.

## Запуск сервера обнаружения

```shell
dvpn server                       # слушает 0.0.0.0:6485
dvpn server -a 0.0.0.0 -p 7000    # свой адрес и порт
```

При первом запуске сервер генерирует ключ Ed25519 и сохраняет его в `config.toml`:

```toml
[local_server]
private_key = "..."    # не передавайте никому
public_key = "..."     # этот ключ указывается у пиров в [servers.*] key
```

Публичный ключ также печатается в лог при каждом старте (`Public key: ...`).
Если удалить секцию `[local_server]`, будет создан новый ключ и его придётся обновить у всех пиров.
Серверу не нужен ключ сети: он не участвует в сессиях между пирами и не видит их трафик.

Откройте на сервере входящий **UDP**-порт (например, `ufw allow 6485/udp`).

> Если у сервера **несколько IP-адресов**, запускайте его с `-a <публичный IP>` — тем же адресом,
> что указан у пиров в `[servers.*] addr`. При `0.0.0.0` ядро может отправить ответ с другого адреса,
> и NAT клиента такой ответ отбросит (клиент застрянет в `connecting`).

Сервер хранит всё только в памяти: сессии без announce дольше 45 с удаляются. Announce подписан ключом узла
и привязан к сессии, поэтому выдать себя за чужой узел перед сервером нельзя.

> Трафик к серверу обнаружения пока **не маскируется** (появится вместе с группами) — его рукопожатие
> узнаваемо для DPI. Трафик между пирами маскируется.

## Запуск как службы

### systemd (Linux)

Пример для узла, установленного в `/opt/dvpn`:

```ini
# /etc/systemd/system/dvpn.service
[Unit]
Description=DVPN node
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/opt/dvpn/dvpn --dir /opt/dvpn
RuntimeDirectory=dvpn
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```shell
sudo systemctl daemon-reload
sudo systemctl enable --now dvpn
journalctl -u dvpn -f
```

Для сервера обнаружения — то же самое с `ExecStart=/opt/dvpn/dvpn --dir /opt/dvpn server`
(root ему не нужен, можно добавить `User=dvpn`, если порт ≥ 1024).

## Справочник config.toml

```toml
[identity]
private_key = "..."         # приватный ключ узла (seed Ed25519, base64url), создаётся сам;
                            # DVPN_PRIVATE_KEY переопределяет; публичный ключ: dvpn show-key

[peer]
bind_addr = "0.0.0.0"       # локальный IPv4 для UDP-сокета
bind_port = "8647-9942"     # порт или диапазон ("8647" или "8647-9942")

[servers.main]              # любое количество секций [servers.<имя>]
addr = "203.0.113.10"       # IPv4 или домен
port = 6485
key = "..."                 # публичный ключ сервера, base64

[net]                       # если секции нет — узел работает без TUN (как с -d)
tun_name = "dnet"           # имя интерфейса (имя адаптера Wintun на Windows)
mtu = 1350
addr = "10.10.33.2"         # свой адрес в сети (см. замечание про peers.json выше)
mask = "255.255.255.0"      # маска или длина префикса: "24"

[group]                     # обязательна для запуска узла
psk = "..."                 # ключ сети: dvpn gen-key, одинаковый у всех узлов

[group.obfs]                # необязательно, см. «Маскировка трафика»; одинаково у всех узлов

[app]
log_level = "INFO"          # TRACE, DEBUG, INFO, WARNING, ERROR (CRITICAL = ERROR)

[local_server]              # создаётся командой dvpn server
private_key = "..."
public_key = "..."
```

Все ключи — base64url без паддинга (43 символа); обычный base64 и паддинг тоже принимаются.
Неизвестные параметры в `[group.obfs]` — ошибка (а не тихое игнорирование), чтобы опечатка не сделала узел
непохожим на остальных. Устаревший `[peer] peer_id` от v3 игнорируется.

**Порт.** Если задан диапазон и все серверы стали недоступны, узел переходит на другой случайный
порт из диапазона — это помогает, когда провайдер или NAT «залип» на старом порте.
Одиночный порт удобен, если вы пробрасываете его на роутере (тогда соединение возможно даже со строгим NAT у собеседника).

**MTU.** Накладные расходы DVPN — 60 байт на пакет (IP + UDP + заголовок 15 + тип 1 + тег шифрования 16)
плюс случайное заполнение (`s4`, по умолчанию до 48 байт). Заполнение урезается так, чтобы UDP-датаграмма не
превышала 1452 байт. 1350 подходит почти везде, включая PPPoE и мобильные сети. Если есть проблемы с большими
пакетами — уменьшите до 1280.

**Формат peers.json** (редактировать руками можно, но лучше через `dvpn set`):

```json
[
  {
    "key": "DZVSMn8lShIWwhSda4umRbtk027yZh_KeJONsPodlFc",
    "name": "alice",
    "addr": "10.10.33.2"
  }
]
```

## Маскировка трафика

Цель — чтобы трафик между пирами не опознавался DPI по сигнатуре (как WireGuard по первым байтам и размерам).
Это не делает DVPN невидимым для анализа потоков (тайминги, объёмы), но убирает дешёвые способы блокировки.

* **Заголовки замаскированы** (как в QUIC): тип пакета, длина заполнения, индексы сессий и счётчики
  зашифрованы ChaCha20 ключом, выведенным из ключа сети. Без psk пакет выглядит как случайные байты.
* **Нет постоянных размеров:** к каждому пакету добавляется случайное заполнение (его длина аутентифицирована).
* **Ключи рукопожатия неотличимы от случайных** — передаются в виде Elligator2-представления.
* **Перед каждым рукопожатием** отправляются мусорные пакеты случайного размера и, если заданы,
  «сигнатурные» пакеты по шаблону (синтаксис AmneziaWG `i1`…`i5`) — например, имитирующие начало TLS или DNS.
* **Таймеры с разбросом:** keepalive, повтор рукопожатий и смена ключей не идут по точному расписанию.

Параметры (значения по умолчанию; диапазон пишется строкой `"a-b"`). **Профиль должен быть одинаковым на всех узлах**:

```toml
[group.obfs]
jc = "4-8"        # число мусорных пакетов перед рукопожатием
jmin = 40         # размер мусорных пакетов, от
jmax = 200        # ... до
s1 = "0-96"       # заполнение инициаций рукопожатия
s2 = "0-96"       # ... ответов на рукопожатие
s4 = "0-48"       # ... пакетов данных
i1 = "<b 0x16030301> <r 32> <t>"   # сигнатурные пакеты i1..i5, отправляются перед мусорными
```

Теги шаблона: `<b 0xHEX>` — фиксированные байты, `<r N>` — N случайных байт, `<rc N>` / `<rd N>` —
случайные буквы / цифры, `<t>` — unix-время (4 байта). Пакет шаблона не должен быть больше 1452 байт.

Параметры AmneziaWG `h1`…`h4` и `s3` не нужны: типы пакетов и так скрыты маскировкой заголовка.

## Справочник команд

Глобальные опции: `--dir <путь>` — каталог с конфигами, `-h` — справка по любой команде.

| Команда | Описание |
|---|---|
| `dvpn` | запустить узел (нужен `[group] psk`) |
| `dvpn -d` | запустить без TUN-интерфейса (только связь с пирами и API) |
| `dvpn -a <адрес>` | адрес API: `127.0.0.1:9902` или путь к unix-сокету |
| `dvpn -v` | версия |
| `dvpn gen-key` | случайный ключ 32 байта (base64url): ключ сети или приватный ключ узла |
| `dvpn show-key [-k приватный_ключ]` | публичный ключ узла (из конфига / `DVPN_PRIVATE_KEY` или из `-k`) |
| `dvpn list` | таблица пиров (Name, Key, Addr) |
| `dvpn set -p <ключ> [-n имя] [-a адрес] [-c]` | добавить пира или изменить его поля |
| `dvpn del -p <ключ>` | удалить пира (себя удалить нельзя) |
| `dvpn export [-j] [-o файл]` | экспорт всех пиров |
| `dvpn import [-i файл] [-c]` | импорт списка пиров |
| `dvpn export-peer [-p ключ] [-j] [-o файл]` | экспорт одного пира (по умолчанию себя) |
| `dvpn import-peer [-i файл]` | импорт одного пира |
| `dvpn server [-a адрес] [-p порт]` | сервер обнаружения |

Везде, где принимается ключ пира (`-p`), достаточно однозначного начала ключа, известного в `peers.json`;
неоднозначное начало — ошибка. Ключ, начинающийся с `-`, тоже можно передавать: `-p -0-goYU…`.

Подробнее про `set`:

* значение `None` очищает поле: `dvpn set -p bob -a None`;
* `-c` / `--clear` — очистить все поля, которые не указаны в команде.

Экспорт по умолчанию — JSON, закодированный в base64 (одна строка, удобно пересылать);
`-j` / `--json` выводит обычный JSON. Импорт принимает оба варианта.
`import -c` перед импортом удаляет всех пиров, кроме себя.

## API

Узел предоставляет локальный API для внешних программ (GUI/TUI, свои сервисы поверх сети).
Транспорт — датаграммы msgpack:

* Linux, если включён TUN и есть права: unix-сокет `/run/dvpn/<tun_name>.sock`;
* иначе (и на Windows): UDP `127.0.0.1:9902`;
* свой адрес: `dvpn -a 127.0.0.1:9000` или `dvpn -a /path/to/api.sock`.

> Любой локальный пользователь, имеющий доступ к сокету, может управлять узлом. Не выставляйте API наружу.

### Подключение

Каждое сообщение — msgpack-словарь с полем `type`. Сначала клиент отправляет
`{"type": "init", "name": "my-app"}`; без этого на остальные запросы приходит `{"type": "close"}`.
Узел шлёт клиенту `{"type": "ping"}` раз в 15 с; клиент должен ответить `{"type": "pong"}`, иначе
примерно через 45 с соединение закрывается. Отключиться — `{"type": "close"}`.

Запросы `get` / `set` / `del` / `route` содержат произвольный `id`, ответ приходит как
`{"type": "res", "id": <тот же id>, "res": <результат>}`.

Узлы везде обозначаются полем `key` — публичным ключом узла (base64url). В запросах можно передать однозначное начало ключа.

Пример на Python:

```python
import socket, msgpack
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.bind(("127.0.0.1", 0))
node = ("127.0.0.1", 9902)
s.sendto(msgpack.dumps({"type": "init", "name": "example"}), node)
s.sendto(msgpack.dumps({"type": "get", "id": 1, "req": "peers"}), node)
print(msgpack.loads(s.recv(65535)))   # {'type': 'res', 'id': 1, 'res': ['DZVS...', ...]}
```

### get

`{"type": "get", "id": 1, "req": "<запрос>", ...}`

| `req` | параметры | результат |
|---|---|---|
| `key` | | свой ключ |
| `peers` | | список ключей |
| `peer_exist` | `key` | bool |
| `peer_name`, `peer_addr` | `key` | строка или nil |
| `peer_sub_args` | `key` | словарь доп. параметров или nil |
| `peer_sub_arg` | `key`, `arg` | значение параметра |
| `peer_endpoint` | `key` | `[ip, port]` или nil |
| `peer_status` | `key` | есть ли прямое соединение |
| `peer_ping` | `key` | RTT в мс (0, если неизвестен) |
| `peer_crypto_status` | `key` | `"noise_ikpsk2"`, если есть сессия, иначе `"no"` |
| `servers` | | список `[ip, port]` |
| `server_status` | `addr: [ip, port]` | подключён ли сервер |
| `server_key` | `addr` | публичный ключ (bytes) |
| `server_last_announce`, `server_last_search`, `server_last_response` | `addr` | unix-время, 0 — никогда |
| `local_addr` | | `[ip, port]` UDP-сокета узла |

### set / del

`{"type": "set", "id": 2, "req": "peer", "key": "...", "name": "...", "addr": "10.10.33.5",
"endpoint": ["1.2.3.4", 5000], "sub_args": {...}, "force": false}` —
поля, которых нет, не меняются; с `"force": true` — очищаются.
Ошибки возвращаются строкой: `key_validate_error`, `key_ambiguous`, `name_not_str`, `addr_validate_error`,
`endpoint_validate_error`, `sub_args_not_dict`, `force_not_bool`.

`{"type": "del", "id": 3, "req": "peer" | "peer_endpoint", "key": "..."}` —
удалить пира или сбросить его текущее соединение. Ошибки: `peer_not_exist`, `error_delete_self_peer`.

### События

Узел рассылает всем клиентам `{"type": "event", "event": {...}}`:

* изменения пиров: `{"action": "add"|"update"|"del", "key", "name", "addr", "endpoint", "sub_args"}`;
* статус сервера: `{"server": [ip, port], "status": bool}`;
* новый замер ping: `{"key": "...", "ping": 12.3}`.

### Свои данные поверх сети (маршруты)

Клиент может занять номер маршрута от 32 до 255 и обмениваться через него произвольными данными с пирами:

```
{"type": "route", "id": 4, "req": "reg", "route": 40}      → nil или "route_exist" / "out_of_range"
{"type": "route", "id": 5, "req": "del", "route": 40}      → nil или "route_not_exist" / "not_permission"
{"type": "route", "id": 6, "req": "routes"}                → [40]
{"type": "net", "rou": 40, "key": "<кому>", "pack": b"данные"}
```

Пакет, пришедший от пира на маршрут 40, будет доставлен занявшему его клиенту в виде
`{"type": "net", "rou": 40, "key": "<от кого>", "pack": b"..."}`. Данные идут по той же сессии, что и IP-трафик.
Пакет должен помещаться в одну датаграмму: не больше ~1400 байт.

## Тестирование и производительность

* **Юнит- и property-тесты** (`cargo test`): Noise IKpsk2 сверяется с [snow](https://github.com/mcginty/snow)
  (байт в байт, обе роли), Elligator2 — с тест-векторами obfs4, окно повторов — с моделью (proptest),
  смена ключей, роуминг, отказ без psk и при чужом psk, повтор рукопожатия, маскировка (энтропия заголовков,
  разброс размеров), подпись announce на сервере обнаружения, конфиг с сохранением комментариев.
* **Фаззинг** (`cargo fuzz`, в CI): разбор IP-пакетов, сообщений сервера обнаружения, приём пакетов от пиров
  (полный путь: маскировка → рукопожатие/данные), payload рукопожатия, шаблоны сигнатурных пакетов.
* **Стенд с TUN и NAT** в network namespaces, без root (`tests/netns-e2e.sh`, через `unshare -rnm`, ~15 с):

```
 a 192.168.1.2 ─ nat1 [masquerade + ct new drop] ─┐                ┌─ nat2 [...] ─ b 192.168.2.2
                                         203.0.113.11 ── «интернет» ── 203.0.113.12
                         сервер обнаружения 203.0.113.1:6485, c 203.0.113.20 (белый адрес)
```

  Проверяется: ping во всех направлениях, прямой путь nat1 → nat2 (hole punching, по счётчику nft),
  отсутствие открытого текста на «интернете», маскировка (нет частого первого байта, ≥10 разных размеров
  на 30 одинаковых ping), iperf3, роуминг при смене внешнего адреса NAT.

```shell
cargo build && tests/netns-e2e.sh                    # нужны unshare, ip, nft, ping; tcpdump и iperf3 — по желанию
cargo test --release -- --ignored --nocapture bench  # бенчмарк шифрования
```

* **CI** (Forgejo Actions, `.gitea/workflows/ci.yml`): `fmt`, `clippy -D warnings`, тесты, фаззинг, netns-стенд.
* Сборка под Windows (`x86_64-pc-windows-gnu`) проверена только компиляцией, запуск на Windows не тестировался.

Скорость: сессия Noise с маскировкой — ~88 000 пакетов/с по 1400 байт на ядро (шифрование + расшифровка),
не медленнее XChaCha20-Poly1305 из 3.x (~85 000 на той же машине). iperf3 на netns-стенде — ~300 Мбит/с,
упирается в общий процессор стенда.

## Переход с версии 3.x

Версия 4 **несовместима** с 3.x ни по протоколу, ни по идентификаторам: сеть переводится целиком,
серверы обнаружения тоже нужно обновить.

1. **Сервер:** обновите бинарник; ключ сервера (`[local_server]`) сохраняется.
2. **Каждый участник:** обновите бинарник и запустите `dvpn list` — в `config.toml` появится `[identity]` с новым
   ключом узла. Старый `[peer] peer_id` больше не используется (его можно удалить).
3. **Ключ сети:** организатор делает `dvpn gen-key` и раздаёт результат всем в `[group] psk`.
   Ключи шифрования пиров из 3.x (`dvpn set -k`) больше не нужны.
4. **Список пиров** собирается заново по шагам 4–6 [настройки](#пошаговая-настройка-сети):
   записи 3.x с 32-символьным `peer_id` v4 не принимает (`Skip peer` в логе). Имена и адреса можно перенести.
5. **API:** поле `peer_id` везде заменено на `key`, запрос `get peer_id` — на `get key`; убраны `peer_crypto`
   и `crypto` в `set`; `peer_crypto_status` возвращает `"noise_ikpsk2"` или `"no"`;
   новые коды ошибок `key_validate_error`, `key_ambiguous`.

Переход с 2.x (Python) описан в README тегов `v2.*` и ветки `master`; сначала переходите на 3.x.

## Решение проблем

Для подробных логов поставьте `log_level = "DEBUG"` в `[app]`.

| Симптом | Причина и решение |
|---|---|
| `[group] psk is required to run a node` | нет ключа сети: добавьте `[group] psk` (одинаковый у всех) |
| `Connection status connecting` повторяется, `connected` не появляется | сервер недоступен или не совпадает ключ: проверьте `addr`/`port`/`key` в `[servers.*]`, открыт ли UDP-порт на сервере; при неверном ключе в логе `Reg session Invalid Signature`; если у сервера несколько IP — запустите его с `-a <публичный IP>` |
| сервер подключён, но пира не находит | пир не запущен, не подключён к тому же серверу или его нет в вашем `peers.json` (и вас — в его); проверьте `dvpn list` у обоих |
| `new endpoint` есть, но в DEBUG нет `session ... established` | разный `[group] psk` или профиль `[group.obfs]`, нет вашего ключа в `peers.json` пира — или NAT не пробивается: симметричный NAT (часто мобильные сети, CGNAT) у обоих участников. Пробросьте порт на роутере у одного из них и задайте фиксированный `bind_port` |
| `packet ... with foreign source dropped` | пир шлёт пакеты не со своего адреса: у него в `peers.json` другой `addr` для себя |
| `Tun init error` | нет прав (root / `CAP_NET_ADMIN` / администратор), на Windows нет `wintun.dll` рядом с exe, либо интерфейс с таким именем уже занят |
| пинг идёт, но большие пакеты (сайты, файлы) зависают | уменьшите `mtu` в `[net]`, например до 1280 |
| оба участника за одним роутером не соединяются | роутер не поддерживает NAT hairpinning; в одной физической сети DVPN не нужен |
