# DVPN

> ### Что это вообще такое?
> Этот проект больше всего похож на [P2PVPN](http://www.p2pvpn.org/)
> и представляет собой шлюз, который создает **прямое соединение** до других пиров. <br><br>

> ### Для чего это можно использовать?
> Этот проект в первую очередь создавался для создания локальной сети в которой все участники сети находятся за nat и не имеют ipv6. <br><br>
> Для меня создание этого проекта решило проблемы с подключением к [Sunshine](https://github.com/LizardByte/Sunshine) на тех ПК которые находятся за nat
> и побочным эффектом стал упавший ping в [cs2](https://store.steampowered.com/app/730/CounterStrike_2/) в тех случаях когда хостом является участник сети, в моем случае ping упал с ~95 на ~30.

> ### Безопасность и анонимность
> DVPN предназначен для частных сетей, участники которых знают друг друга.
> Узел опознаётся по своему **публичному ключу** — его можно показывать кому угодно.
> Секреты — **приватный ключ узла** (`[identity]`), **секрет группы** (у админа) и **invite-строки**:
> по invite один узел входит в группу. Не публикуйте их и передавайте только по защищённому каналу. <br>
> Если вашей целью является именно анонимность используйте [Yggdrasil](https://yggdrasil-network.github.io/) + [wireguard](https://www.wireguard.com/) или [i2p](https://geti2p.net/en/), [tor](https://www.torproject.org/).

> [!WARNING]
> **Ветка `DVPN-rs` — версия 4 в разработке.** Протокол v4 **несовместим** с 3.x: узлы v3 и v4 друг друга
> не видят, сеть переводится целиком (см. [Переход с версии 3.x](#переход-с-версии-3x)).
> Формат конфига и CLI ещё будут меняться. План — [PLAN.md](PLAN.md), ход работ — [PROGRESS.md](PROGRESS.md).

## Состояние версии 4

Готово (этапы 0–2 и часть этапа 3 [PROGRESS.md](PROGRESS.md)):

* **идентичность по ключу:** узел — это пара ключей Ed25519, его id — публичный ключ (43 символа base64url);
  подделать чужой id ни перед пирами, ни перед сервером обнаружения нельзя;
* **группы и вход по invite:** админ создаёт группу и выдаёт invite-строки; узел входит одной командой,
  без ручного обмена ключами и списками. Членство подтверждает **сертификат**, подписанный ключом группы:
  в нём имя узла и его адрес в сети. Invite одноразовый; админ исключает узел одной командой, отзыв доходит
  до всех участников за секунды, и psk группы меняется без разрыва связи; сертификаты продлеваются
  автоматически, пока админ иногда бывает в сети;
* **сессии Noise IKpsk2** (как в WireGuard): взаимная аутентификация по ключам узлов + psk группы + сертификат,
  прямая секретность, смена ключей каждые ~2 минуты, защита от повторов, переход на новый адрес (roaming) только
  по аутентифицированным пакетам;
* **маскировка:** ни одного постоянного байта и размера на проводе, ключи рукопожатия неотличимы от случайных
  (Elligator2), мусорные и «сигнатурные» пакеты перед рукопожатием — см. [Маскировка трафика](#маскировка-трафика).

Также есть: IPv6 внутри сети (у каждого узла адрес в ULA группы), подсети за узлами (site-to-site) и выход
в интернет через узел сети (exit) — см. [Маршруты](#маршруты-подсети-за-узлами-и-выход-в-интернет).

Связь через других участников (mesh): узлы, которые друг друга напрямую не видят, общаются через узлы-ретрансляторы,
путь выбирается автоматически и меняется при падении ретранслятора — см. [Ретрансляторы](#ретрансляторы-mesh).

Ещё нет (следующие этапы): несколько групп на одном узле, автоматическая
настройка NAT на exit-узле, системные маршруты на Windows и macOS.

## Как это работает

```
   пир A (за NAT)                 сервер обнаружения                 пир B (за NAT)
  ┌───────────────┐    announce     ┌─────────────┐    announce     ┌───────────────┐
  │ TUN 10.10.33.2│ ──────────────► │ dvpn server │ ◄────────────── │ TUN 10.10.33.3│
  │     dvpn      │ ◄── адрес B ─── │  UDP 6485   │ ─── адрес A ──► │     dvpn      │
  └──────┬────────┘                 └─────────────┘                 └───────┬───────┘
         │                                                                  │
         └───── прямой UDP-туннель (hole punching), Noise IKpsk2 + маскировка ┘
```

1. Каждый узел открывает **один** UDP-сокет и через него подключается к серверам обнаружения. Сессия с сервером
   устроена так же, как между узлами (Noise IKpsk2, маскировка), ключи маскировки выводятся из публичного ключа
   сервера: рукопожатие доказывает и ключ сервера, и ключ узла.
2. Узел сообщает серверу сертификат своей группы (announce). Сервер
   проверяет сертификат по id группы и держит список участников группы, которые сейчас в сети.
3. Сервер сообщает узлу всех участников его группы (их сертификаты и внешние адреса IP:порт), а им — о новом узле.
   Узел сам перепроверяет каждый сертификат: серверу членство не доверяется.
4. Пиры начинают слать друг другу рукопожатия Noise с того же сокета, это пробивает NAT (UDP hole punching).
   Рукопожатие проходит, только если у обоих psk группы и действующий сертификат на свой ключ.
5. После рукопожатия пиры обмениваются keepalive раз в 12–18 с; если пир молчит 45 с, адрес сбрасывается
   и поиск начинается заново. Если пакет сессии пришёл с другого адреса (NAT выдал другой порт, сменилась сеть),
   узел переключается на новый адрес (roaming).
6. IP-пакеты из TUN-интерфейса отправляются напрямую нужному пиру (по его адресу в локальной сети),
   шифруясь ChaCha20-Poly1305 ключами текущей сессии. Сервер обнаружения трафик **не** пропускает через себя.

Сервер нужен только для знакомства пиров. Если он недоступен, уже установленные соединения продолжают работать.

## Сборка

Нужен Rust 1.85+ ([rustup.rs](https://rustup.rs/)).

```shell
git clone https://git.mihprog.com/DVPN/DVPN.git
cd DVPN
git switch DVPN-rs
cargo build --release
# бинарник: target/release/dvpn (dvpn.exe на Windows)
```

### Linux

Для создания TUN-интерфейса нужны права root или capability `CAP_NET_ADMIN`:

```shell
sudo setcap cap_net_admin+ep target/release/dvpn   # чтобы запускать без sudo
```

Без root по умолчанию не получится создать unix-сокет API в `/run/dvpn`, тогда API автоматически
слушает `127.0.0.1:9902` (или укажите свой адрес через `-a`).

### Windows

1. Скачайте [Wintun](https://www.wintun.net/) и положите `wintun.dll` (из папки под вашу архитектуру,
   обычно `bin/amd64`) **рядом с `dvpn.exe`**.
2. Запускайте из консоли **от имени администратора**.
3. Разрешите `dvpn.exe` в брандмауэре Windows (входящий UDP), иначе пиры не смогут достучаться.

Кросс-сборка под Windows с Linux:

```shell
rustup target add x86_64-pc-windows-gnu
cargo build --release --target x86_64-pc-windows-gnu   # нужен mingw-w64
```

## Файлы и каталог данных

| Файл          | Назначение                                                                                   |
|---------------|----------------------------------------------------------------------------------------------|
| `config.toml` | ключ узла, группы (psk, сертификат, у админа — секрет группы), порты, серверы, TUN, логи      |
| `state.bin`   | записи группы, подписанные её ключом: отзывы, выданные админом сертификаты, смены psk       |

Список участников на диске не хранится: узел узнаёт их от сервера обнаружения, имя и адрес каждого — из его
сертификата.

По умолчанию файлы лежат **рядом с бинарником**. Другой каталог можно задать опцией `--dir <путь>` или
переменной окружения `DVPN_DIR` (действует для всех команд).

При первом запуске любой команды создаётся `config.toml` по умолчанию с новым ключом узла (секция `[identity]`).
`config.toml` записывается с правами `0600` — в нём секреты. Приватный ключ можно не хранить в файле, а передавать
переменной окружения `DVPN_PRIVATE_KEY`.

## Пошаговая настройка сети

Пример: Алиса создаёт сеть и приглашает Боба. Нужен один сервер обнаружения.

### 1. Сервер обнаружения

На машине с белым IP (VPS) — см. [Запуск сервера обнаружения](#запуск-сервера-обнаружения).
Запомните его **IP, порт и публичный ключ**.

### 2. Алиса: сервер и группа

```shell
dvpn show-key        # создаст config.toml с ключом узла
```

Добавьте сервер в `config.toml` (серверов можно несколько: `[servers.msk]`, `[servers.am]`, …):

```toml
[servers.main]
addr = "203.0.113.10"     # IP или доменное имя сервера
port = 6485
key = "-0-goYUMWn2jfZ2QgYhvS489mWf7G4tgS86dZK18Izo"   # публичный ключ из вывода `dvpn server`
```

Создайте группу — Алиса станет её админом:

```shell
dvpn group create home -a 10.10.33.1 -n alice
```

* `-a` — свой адрес в сети (по умолчанию случайный из `10.10.33.0` с маской `[net] mask`);
* `-n` — своё имя в группе.

Секрет группы записан в `config.toml` (`[[groups]] secret`). **Сделайте резервную копию**: без секрета нельзя
приглашать, исключать, продлевать сертификаты и менять psk, а восстановить его нельзя:

```shell
dvpn group backup -o home.bak        # спросит пароль (или DVPN_BACKUP_PASSWORD); храните файл офлайн
dvpn group restore -i home.bak       # на другом узле: он станет админом группы (со своим ключом,
                                     # или --with-key — с ключом прежнего узла админа)
```

Файл зашифрован паролем (Argon2id, 64 МиБ, + XChaCha20-Poly1305) и содержит секрет группы, текущую эпоху psk,
профиль маскировки, серверы обнаружения, статические узлы, сертификат и ключ узла админа.

### 3. Алиса: invite для Боба

```shell
dvpn group invite -n bob -a 10.10.33.2    # печатает invite-строку
```

* `-a` — адрес Боба в сети (по умолчанию случайный свободный из сети группы — следите, чтобы адреса не повторялись);
* `--ttl` — сколько часов invite действует (по умолчанию 24).

Invite — одноразовый пропуск в группу: в нём psk группы, профиль маскировки, серверы обнаружения и join-ключ.
Передайте его Бобу по защищённому каналу. Когда узел Алисы увидит Боба в сети, он выдаст Бобу обычный сертификат
и погасит invite: второй узел по нему уже не войдёт (сервер обнаружения не пустит второй узел и раньше).

### 4. Боб: вход в группу

```shell
dvpn group join <invite>     # без аргумента строку можно вставить в консоль, или -i файл
dvpn group list
```

Сервер обнаружения добавится в `config.toml` Боба из invite. Больше ничего настраивать не нужно: остальных
участников узлы находят сами.

### 5. Запуск

```shell
sudo dvpn
```

В логах должно появиться `Connection status connected` (подключение к серверу), затем
`Peer bob(…) new endpoint 1.2.3.4:5678`. Проверка:

```shell
ping 10.10.33.2
```

С `log_level = "DEBUG"` видны рукопожатия (`Link | session with bob(…) established`) и keepalive с замером RTT.

### Без сервера обнаружения: статические узлы

Если у узла есть постоянный адрес (белый IP или проброшенный порт), к нему можно подключаться напрямую — сервер
обнаружения тогда не нужен вовсе. Задайте этому узлу фиксированный порт (`[peer] bind_port = "7000"`) и при
выдаче invite укажите адрес:

```shell
dvpn group invite -n bob --static 203.0.113.10:7000     # можно несколько --static, можно доменное имя
```

Боб получит в `config.toml` секцию `[[static_peers]]` и будет подключаться к узлу Алисы сам. Ту же секцию
можно написать и руками:

```toml
[[static_peers]]
key = "DZVSMn8lShIWwhSda4umRbtk027yZh_KeJONsPodlFc"      # ключ узла (dvpn show-key на нём)
endpoints = ["203.0.113.10:7000", "vpn.example.com:7000"]
```

Пока сессии нет, узел шлёт рукопожатие сразу на все адреса (имена разрешаются заново при каждой попытке, IPv6 и
IPv4), увеличивая паузу между попытками от 1 с до минуты; какой адрес ответит первым, тот и используется.

### Маршруты: подсети за узлами и выход в интернет

Кроме своего адреса узел может обслуживать **подсети**: локальную сеть за ним (site-to-site) или весь интернет
(exit). Подсеть, которую узел вправе анонсировать, админ записывает в его сертификат — подделать её нельзя:

```shell
dvpn group create home -a 10.10.33.1 --route 192.168.10.0/24      # LAN за узлом админа
dvpn group invite -n office -a 10.10.33.3 --route 192.168.30.0/24  # LAN за новым узлом
```

Все участники направляют эти подсети соответствующему узлу (таблица CKR) и ставят системные маршруты. На узле, за
которым подсеть, включите пересылку (`sysctl net.ipv4.ip_forward=1`), а хостам LAN укажите маршрут через него.

**Выход в интернет через узел сети (exit).** Каждый узел сам выбирает шлюзы — один, несколько по приоритету или
ни одного:

```shell
dvpn exit --v4 vps1,vps2          # IPv4-интернет через vps1, если он недоступен — через vps2
dvpn exit --v6 vps1               # IPv6-интернет (2000::/3) через vps1
dvpn exit --none                  # без шлюза: интернет напрямую, как без DVPN
dvpn exit                         # показать текущие
```

Шлюзы указываются именами участников или ключами и пишутся в `[exit]` в `config.toml`; работающий узел подхватывает
изменение за секунду. Используется первый живой шлюз (с прямой связью или путём через ретрансляторы); если он
пропал, трафик сразу уходит на следующий, а на вернувшийся более приоритетный — через 30 с его стабильной работы.
На шлюзе нужна секция `[gateway]` (ниже).
Через шлюз идут все публичные IPv4 (`inetv4`), частные сети остаются локальными. Пока ни один шлюз не доступен,
интернет блокируется (**kill switch**): публичные адреса остаются в туннеле, где их некому нести, и ничего не
утекает мимо него; свой трафик DVPN при этом работает. Отключить: `dvpn exit --kill-switch off` — тогда без шлюза
интернет идёт напрямую.

**DNS через шлюз.** `dvpn exit --dns 1.1.1.1,9.9.9.9` — пока шлюз активен, DNS-сервер узла пересылает все имена
(кроме `.dvpn`) на эти серверы через туннель, а systemd-resolved отправляет ему все запросы. Так DNS-запросы не
уходят к провайдеру или домашнему роутеру. `--dns none` — убрать.

**Узел-шлюз** настраивается секцией `[gateway]` (Linux, nftables):

```toml
[gateway]
wan = ["ens3"]              # интерфейсы в интернет: туда маскарадится трафик из туннеля
ndp_proxy = "ens3"          # необязательно: публичные IPv6 участников из префикса этого интерфейса
manage_sysctl = true        # включить пересылку (ip_forward, IPv6 forwarding, proxy_ndp)
```

Шлюз включает пересылку (на WAN-интерфейсах ставит `accept_ra = 2`, чтобы не потерять свой IPv6-маршрут из RA),
маскарадит IPv4 и IPv6 с ULA-адресов группы и подрезает TCP MSS под MTU туннеля. **Публичный IPv6 участнику:** админ
даёт ему адрес из префикса шлюза в сертификате (`dvpn group invite -n phone --route 2a01:db8:4:390::6/128`); узел
вешает его на TUN, а шлюз отвечает за него по NDP proxy на `ndp_proxy` и маршрутизирует в туннель (как
`ndp_proxy_interface` в yggmgr). Чтобы такой участник выходил в IPv6-интернет через шлюз: `dvpn exit --v6 <шлюз>`.
При остановке узел убирает свою таблицу nft, NDP proxy и маршруты.

Свои маршруты узел задаёт в `config.toml` — они перекрывают маршруты из сертификатов и шлюзов:

```toml
[ckr.remote_subnets]
"<ключ узла>" = ["192.168.50.0/24", "~10.0.0.0/8"]
```

Синтаксис записей (как CKR в Yggdrasil): `10.0.0.0/24` или адрес без маски — маршрут; `~10.0.0.0/8` — только
внутри DVPN, без системного маршрута; `!192.168.1.0/24` — исключение («не через туннель»); `inetv4` / `inetv6` —
публичные IPv4 / `2000::/3`. Exit-узлу нужна секция `[gateway]` (см. «Выход в интернет»).

Пакет от соседа принимается, только если его источник маршрутизируется обратно к этому соседу: узел вставляет
пакеты только со своих адресов и подсетей, а из интернета — только exit-узел, которому вы это разрешили.

**Системные маршруты (Linux).** Узел ставит их в отдельную таблицу `7347` с правилами `ip rule` (как `wg-quick`):
маршруты локальной сети в основной таблице остаются главнее, а свой трафик DVPN (сервер обнаружения, соседи)
помечен fwmark `0x7347` и в туннель не попадает — даже при маршруте по умолчанию через exit-узел. Правила и
таблица снимаются при остановке (Ctrl+C, SIGTERM) и при старте после сбоя. Отключить: `[net] manage_routes = false`.
На Windows и macOS маршруты пока нужно ставить вручную.

**IPv6 внутри сети.** Каждый узел получает на TUN адрес из ULA-префикса группы (`fdXX:…/48`), выведенный из ключа
узла: его не нужно раздавать, и подделать его нельзя. Свой адрес видно в `ip -6 addr show dnet`.

### Изменение участников: dvpn node

Адреса, подсети и роли участника записаны в его сертификате. Админ меняет их на лету — без нового invite:

```shell
dvpn node list                                   # участники: адреса, подсети, роли, срок сертификата
dvpn node set office --add-route 192.168.31.0/24 # ещё одна подсеть за узлом
dvpn node set phone --addr 10.10.33.40           # новый адрес в сети
dvpn node set phone --add-route 2a01:db8:4:390::7/128   # публичный IPv6 (через NDP proxy шлюза)
dvpn node set vps2 --relay                       # сделать ретранслятором (--no-relay — снять)
```

Команда выпускает участнику новый сертификат и кладёт его в записи группы; работающий узел админа за секунды
рассылает его через сервер обнаружения и соседей. Все участники сразу обновляют маршруты, а сам участник
переносит адреса на своём TUN. В `group invite` свободный адрес выбирается с учётом уже выданных.

### Доступ внутри сети: dvpn acl

По умолчанию любой участник может обратиться к любому. Админ может ограничить это правилами — они одинаковы для
всех узлов группы:

```toml
# acl.toml
default = "allow"                     # или "deny": что не попало ни под одно правило
[tags]
servers = ["msk-firstvds", "posad"]   # имена участников или ключи
[[rule]]
from = ["phone"]                      # теги, участники или "*"
to = ["servers"]
proto = "tcp"                         # tcp, udp, icmp или any
ports = ["22", "80-443"]
action = "allow"
[[rule]]
from = ["*"]
to = ["servers"]
action = "deny"
```

```shell
dvpn acl set acl.toml     # проверить и сделать правилами группы (только админ)
dvpn acl show             # текущие правила в том же формате
dvpn acl clear            # снять все правила
```

Каждый узел применяет правила, в которых он указан в `to`, к трафику из туннеля к себе и к подсетям за собой (первое
совпадение решает). Ответы на собственные соединения узла проходят всегда; трафик не от участников (интернет через
exit) правила не трогают. Применяются через nftables (`table inet dvpn_acl`), пока только на Linux.

### Имена участников: DNS

Каждый узел отвечает на DNS-запросы на своём адресе в сети за зону `.dvpn`: `phone.dvpn` и `phone.home.dvpn`
(имя участника, имя группы) дают его IPv4, адрес в ULA и публичный IPv6, если он есть. Если в системе работает
systemd-resolved, узел сам делает `.dvpn` split-DNS-доменом интерфейса туннеля — остальные запросы идут как раньше.
Без resolved направьте `*.dvpn` на адрес узла вручную.

Те же имена доступны через **mDNS** как `phone.local`: узел ставит интерфейсу туннеля флаг multicast и отвечает на
mDNS-запросы, которые система шлёт в туннель (avahi / nss-mdns, systemd-resolved — узел включает ему mDNS на этом
интерфейсе). Так имена работают и там, где DNS не настроен.

Настройки — секция `[dns]`:

```toml
[dns]
enable = true             # по умолчанию включено, если есть TUN
domain = "dvpn"
manage_resolved = true
```

### Ретрансляторы (mesh)

Если два узла не могут связаться напрямую (оба за строгим NAT, разные сети, фильтры), их трафик идёт через
**ретрансляторы** — узлы с ролью `relay` (обычно с белым адресом или хорошим каналом):

```shell
dvpn group create home --relay                   # узел админа ретранслирует
dvpn group invite -n vps2 --relay                # и этот тоже
```

Каждый узел объявляет своих прямых соседей и задержку до них, по этим данным все считают кратчайшие пути
(link-state, как OSPF). Через ретранслятор идёт сквозная сессия: ретранслятор видит только, кому переслать
пакет, но не его содержимое. Пути через несколько ретрансляторов поддерживаются. Если ретранслятор пропал, путь
за ~30 с переходит на другой; пока используется ретранслятор, узлы продолжают пробивать прямой путь и
переходят на него, как только он заработал.

`traceroute` / `tracepath` показывают ретрансляторы как обычные маршрутизаторы — по их адресам внутри сети
(IPv4 из сертификата или ULA): ретранслятор не видит IP-заголовок (он зашифрован), поэтому TTL переносится в
заголовок пересылки, а ICMP Time Exceeded от имени ретранслятора формирует узел-источник.

### Исключение узла и продление сертификатов

```shell
dvpn group members           # у админа: кто вступал (имя, ключ, адрес, срок сертификата)
dvpn group revoke bob        # имя, ключ или однозначное начало ключа; --in 120 — через сколько секунд сменить psk
dvpn group rotate            # сменить psk группы без исключения (например, если invite мог утечь)
```

Отзыв — запись, подписанная ключом группы. Работающий узел админа подхватывает её из `state.bin` за секунду и
рассылает через сервер обнаружения и напрямую участникам; они разрывают сессии с исключённым узлом и больше не
принимают его рукопожатия, сервер убирает его из списка группы. Записи хранятся у всех участников и у сервера,
поэтому отзыв доходит и до тех, кто был офлайн.

Вместе с отзывом админ меняет psk группы (`--no-rotate` — не менять): новый psk шифруется отдельно ключу
каждого участника, исключённый его не получает. Узлы сразу начинают принимать оба psk, через `--in` секунд
(по умолчанию 120) переходят на новый и ещё 10 минут принимают старый — связь при смене не рвётся. Участник,
который был офлайн всё это время, получит новый psk при подключении (записи хранит и сервер), а до того
останется без связи с остальными.

Сертификаты выдаются на 30 дней. Узел админа продлевает их сам, когда до конца срока меньше 10 дней и участник в
сети; новый сертификат узел сохраняет в `config.toml`. Если админа долго нет в сети, участник с истёкшим
сертификатом выпадает из группы — нужен новый invite (пока узел может состоять только в одной группе: сначала
`dvpn group leave`).

## Запуск сервера обнаружения

```shell
dvpn server                       # слушает [::]:6485 — IPv6 и IPv4 на одном сокете
dvpn server -a 203.0.113.10 -p 7000    # свой адрес и порт (только этот адрес и его семейство)
```

При первом запуске сервер генерирует ключ Ed25519 и сохраняет его в `config.toml`:

```toml
[local_server]
private_key = "..."    # не передавайте никому
public_key = "..."     # этот ключ указывается у пиров в [servers.*] key
```

Публичный ключ также печатается в лог при каждом старте (`Public key: ...`).
Если удалить секцию `[local_server]`, будет создан новый ключ и его придётся обновить у всех пиров.
Серверу не нужны секреты групп: он проверяет сертификаты по id группы (публичному ключу), не участвует в сессиях
между пирами и не видит их трафик. Он видит id групп и ключи их участников.

Откройте на сервере входящий **UDP**-порт (например, `ufw allow 6485/udp`).

> Если у сервера **несколько IP-адресов**, запускайте его с `-a <публичный IP>` — тем же адресом,
> что указан у пиров в `[servers.*] addr`. При `::` ядро может отправить ответ с другого адреса,
> и NAT клиента такой ответ отбросит (клиент застрянет в `connecting`).

Сервер хранит всё только в памяти: клиенты, от которых ничего не было 45 с, удаляются. Ключ узла доказан
рукопожатием сессии, поэтому выдать себя за чужой узел перед сервером нельзя. Сессию сервер находит по её
индексу, а не по адресу клиента: если у клиента сменился внешний адрес (NAT, переход между сетями), сессия
продолжается, а участники группы узнают новый адрес.

Трафик к серверу замаскирован так же, как между узлами: по виду пакетов сервер не отличить от участника сети.
От активного зондирования: на случайные пакеты и на повтор перехваченного рукопожатия сервер не отвечает
(рукопожатие несёт метку времени, допустимое расхождение часов — 10 минут), ответ никогда не больше запроса.

## Запуск как службы

### systemd (Linux)

Пример для узла, установленного в `/opt/dvpn`:

```ini
# /etc/systemd/system/dvpn.service
[Unit]
Description=DVPN node
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/opt/dvpn/dvpn --dir /opt/dvpn
RuntimeDirectory=dvpn
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```shell
sudo systemctl daemon-reload
sudo systemctl enable --now dvpn
journalctl -u dvpn -f
```

Для сервера обнаружения — то же самое с `ExecStart=/opt/dvpn/dvpn --dir /opt/dvpn server`
(root ему не нужен, можно добавить `User=dvpn`, если порт ≥ 1024).

## Справочник config.toml

```toml
[identity]
private_key = "..."         # приватный ключ узла (seed Ed25519, base64url), создаётся сам;
                            # DVPN_PRIVATE_KEY переопределяет; публичный ключ: dvpn show-key

[peer]
bind_addr = "::"            # "::" — IPv6 и IPv4 на одном сокете; "0.0.0.0" — только IPv4
bind_port = "8647-9942"     # порт или диапазон ("8647" или "8647-9942")

[servers.main]              # любое количество секций [servers.<имя>]
addr = "203.0.113.10"       # IPv4, IPv6 или домен (пробуются все адреса сразу)
port = 6485
key = "..."                 # публичный ключ сервера, base64

[net]                       # если секции нет — узел работает без TUN (как с -d)
tun_name = "dnet"           # имя интерфейса (имя адаптера Wintun на Windows)
mtu = 1350
mask = "255.255.255.0"      # маска сети группы или длина префикса: "24"; свой адрес — из сертификата
manage_routes = true        # ставить системные маршруты для подсетей и exit (Linux)

[exit]                      # шлюзы в интернет по приоритету (dvpn exit), пусто — без шлюза
v4 = ["vps1", "vps2"]
v6 = []
kill_switch = true          # шлюзы заданы, но недоступны: интернет блокируется (по умолчанию)
dns = ["1.1.1.1"]           # DNS через шлюз, пока он активен

[ckr.remote_subnets]        # свои маршруты поверх маршрутов из сертификатов
"<ключ узла>" = ["192.168.50.0/24", "~10.0.0.0/8"]

[[groups]]                  # пишется командами dvpn group create / join
name = "home"               # локальное имя группы
id = "..."                  # id группы (её публичный ключ)
secret = "..."              # секрет группы — только у админа; у участников вместо него psk = "..."
epoch = 0
cert = "..."                # сертификат этого узла (имя, адрес), подписан группой

[[static_peers]]            # узлы с постоянным адресом: подключаться напрямую, без сервера обнаружения
key = "..."
endpoints = ["203.0.113.10:7000"]

[groups.obfs]               # необязательно, см. «Маскировка трафика»; у всех участников из invite

[app]
log_level = "INFO"          # TRACE, DEBUG, INFO, WARNING, ERROR (CRITICAL = ERROR)

[local_server]              # создаётся командой dvpn server
private_key = "..."
public_key = "..."
```

Все ключи — base64url без паддинга (43 символа); обычный base64 и паддинг тоже принимаются.
Неизвестные параметры в `[groups.obfs]` — ошибка (а не тихое игнорирование), чтобы опечатка не сделала узел
непохожим на остальных. Устаревшие `[peer] peer_id`, `[net] addr` и `[group] psk` игнорируются.
Пока узел может состоять только в одной группе (несколько групп — пункт 3.5 этапа 3).

**IPv4 и IPv6.** Узел работает через один UDP-сокет на оба семейства. Серверу обнаружения он сообщает адреса своих
интерфейсов (кандидаты: локальная сеть, IPv6), сервер добавляет адрес, который видит сам, и раздаёт этот список
участникам. Рукопожатие уходит сразу на все адреса собеседника, побеждает первый ответивший — так узлы в одной
локальной сети связываются напрямую, а при IPv6 у обоих — без NAT. Адреса интерфейсов видны серверу и участникам
группы. В старых конфигах `bind_addr = "0.0.0.0"` — это только IPv4; замените на `"::"`.

**Порт.** Если задан диапазон и все серверы стали недоступны, узел переходит на другой случайный
порт из диапазона — это помогает, когда провайдер или NAT «залип» на старом порте.
Одиночный порт удобен, если вы пробрасываете его на роутере (тогда соединение возможно даже со строгим NAT у собеседника).

**MTU.** Накладные расходы DVPN — 60 байт на пакет (IP + UDP + заголовок 15 + тип 1 + тег шифрования 16)
плюс случайное заполнение (`s4`, по умолчанию до 48 байт). Заполнение урезается так, чтобы UDP-датаграмма не
превышала 1452 байт. 1350 подходит почти везде, включая PPPoE и мобильные сети. Если есть проблемы с большими
пакетами — уменьшите до 1280.

## Маскировка трафика

Цель — чтобы трафик между пирами не опознавался DPI по сигнатуре (как WireGuard по первым байтам и размерам).
Это не делает DVPN невидимым для анализа потоков (тайминги, объёмы), но убирает дешёвые способы блокировки.

* **Сервер обнаружения не выделяется:** сессия с ним устроена так же, как между узлами, и не отвечает зондам.
* **Заголовки замаскированы** (как в QUIC): тип пакета, длина заполнения, индексы сессий и счётчики
  зашифрованы ChaCha20 ключом, выведенным из psk группы. Без psk пакет выглядит как случайные байты.
* **Нет постоянных размеров:** к каждому пакету добавляется случайное заполнение (его длина аутентифицирована).
* **Ключи рукопожатия неотличимы от случайных** — передаются в виде Elligator2-представления.
* **Перед каждым рукопожатием** отправляются мусорные пакеты случайного размера и, если заданы,
  «сигнатурные» пакеты по шаблону (синтаксис AmneziaWG `i1`…`i5`) — например, имитирующие начало TLS или DNS.
* **Таймеры с разбросом:** keepalive, повтор рукопожатий и смена ключей не идут по точному расписанию.

Параметры (значения по умолчанию; диапазон пишется строкой `"a-b"`). **Профиль должен быть одинаковым на всех
узлах**: админ задаёт его в `[groups.obfs]` до выдачи invite, участники получают его в invite.

```toml
[groups.obfs]
jc = "4-8"        # число мусорных пакетов перед рукопожатием
jmin = 40         # размер мусорных пакетов, от
jmax = 200        # ... до
s1 = "0-96"       # заполнение инициаций рукопожатия
s2 = "0-96"       # ... ответов на рукопожатие
s4 = "0-48"       # ... пакетов данных
i1 = "<b 0x16030301> <r 32> <t>"   # сигнатурные пакеты i1..i5, отправляются перед мусорными
```

Теги шаблона: `<b 0xHEX>` — фиксированные байты, `<r N>` — N случайных байт, `<rc N>` / `<rd N>` —
случайные буквы / цифры, `<t>` — unix-время (4 байта). Пакет шаблона не должен быть больше 1452 байт.

Параметры AmneziaWG `h1`…`h4` и `s3` не нужны: типы пакетов и так скрыты маскировкой заголовка.

## Справочник команд

Глобальные опции: `--dir <путь>` — каталог с конфигами, `-h` — справка по любой команде.

| Команда | Описание |
|---|---|
| `dvpn` | запустить узел (нужна группа: `group create` или `group join`) |
| `dvpn -d` | запустить без TUN-интерфейса (только связь с пирами и API) |
| `dvpn -a <адрес>` | адрес API: `127.0.0.1:9902` или путь к unix-сокету |
| `dvpn -v` | версия |
| `dvpn gen-key` | случайный ключ 32 байта (base64url), например приватный ключ узла |
| `dvpn show-key [-k приватный_ключ]` | публичный ключ узла (из конфига / `DVPN_PRIVATE_KEY` или из `-k`) |
| `dvpn node list [-g группа]` | участники: адреса, подсети, роли |
| `dvpn node set <узел> [--addr IP] [--add-route P] [--del-route P] [--relay\|--no-relay] [--name N]` | изменить участника (только админ) |
| `dvpn acl set <файл> \| show \| clear` | правила доступа внутри группы (set/clear — только админ) |
| `dvpn exit [--v4 шлюзы] [--v6 шлюзы] [--none] [--kill-switch on\|off] [--dns IP,…]` | шлюзы в интернет по приоритету (через запятую) |
| `dvpn group create <имя> [-a адрес] [-n имя_узла] [--route подсеть] [--relay]` | создать группу, этот узел — её админ |
| `dvpn group invite [-g группа] [-n имя] [-a адрес] [--ttl часы] [--static host:port] [--route подсеть] [--relay]` | invite для одного нового узла (только админ) |
| `dvpn group join [invite] [-i файл]` | войти в группу по invite |
| `dvpn group list` | группы узла: роль, имя и адрес в группе, срок сертификата |
| `dvpn group members [-g группа]` | участники по записям группы: имя, ключ, адрес, срок или «revoked» |
| `dvpn group revoke <узел> [-g группа] [--in сек] [--no-rotate]` | исключить узел и сменить psk (только админ) |
| `dvpn group rotate [-g группа] [--in сек]` | сменить psk группы (только админ) |
| `dvpn group backup [-g группа] [-o файл]` | зашифрованная паролем копия секрета группы и данных админа |
| `dvpn group restore [-i файл] [--with-key]` | стать админом группы из копии |
| `dvpn group leave <группа>` | выйти из группы (удалить её из `config.toml`) |
| `dvpn server [-a адрес] [-p порт]` | сервер обнаружения |

Участники группы, которые сейчас в сети, видны через API (`get peers`, `peer_name`, `peer_addr`, …).

## API

Узел предоставляет локальный API для внешних программ (GUI/TUI, свои сервисы поверх сети).
Транспорт — датаграммы msgpack:

* Linux, если включён TUN и есть права: unix-сокет `/run/dvpn/<tun_name>.sock`;
* иначе (и на Windows): UDP `127.0.0.1:9902`;
* свой адрес: `dvpn -a 127.0.0.1:9000` или `dvpn -a /path/to/api.sock`.

> Любой локальный пользователь, имеющий доступ к сокету, может управлять узлом. Не выставляйте API наружу.

### Подключение

Каждое сообщение — msgpack-словарь с полем `type`. Сначала клиент отправляет
`{"type": "init", "name": "my-app"}`; без этого на остальные запросы приходит `{"type": "close"}`.
Узел шлёт клиенту `{"type": "ping"}` раз в 15 с; клиент должен ответить `{"type": "pong"}`, иначе
примерно через 45 с соединение закрывается. Отключиться — `{"type": "close"}`.

Запросы `get` / `set` / `del` / `route` содержат произвольный `id`, ответ приходит как
`{"type": "res", "id": <тот же id>, "res": <результат>}`.

Узлы везде обозначаются полем `key` — публичным ключом узла (base64url). В запросах можно передать однозначное начало ключа.

Пример на Python:

```python
import socket, msgpack
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.bind(("127.0.0.1", 0))
node = ("127.0.0.1", 9902)
s.sendto(msgpack.dumps({"type": "init", "name": "example"}), node)
s.sendto(msgpack.dumps({"type": "get", "id": 1, "req": "peers"}), node)
print(msgpack.loads(s.recv(65535)))   # {'type': 'res', 'id': 1, 'res': ['DZVS...', ...]}
```

### get

`{"type": "get", "id": 1, "req": "<запрос>", ...}`

| `req` | параметры | результат |
|---|---|---|
| `key` | | свой ключ |
| `peers` | | список ключей |
| `peer_exist` | `key` | bool |
| `peer_name`, `peer_addr` | `key` | строка или nil |
| `peer_sub_args` | `key` | словарь доп. параметров или nil |
| `peer_sub_arg` | `key`, `arg` | значение параметра |
| `peer_endpoint` | `key` | `[ip, port]` или nil |
| `peer_status` | `key` | есть ли прямое соединение |
| `peer_ping` | `key` | RTT в мс (0, если неизвестен) |
| `peer_crypto_status` | `key` | `"noise_ikpsk2"`, если есть сессия, иначе `"no"` |
| `servers` | | список `[ip, port]` |
| `server_status` | `addr: [ip, port]` | подключён ли сервер |
| `server_key` | `addr` | публичный ключ (bytes) |
| `server_last_announce`, `server_last_search`, `server_last_response` | `addr` | unix-время, 0 — никогда |
| `local_addr` | | `[ip, port]` UDP-сокета узла |

### set / del

`{"type": "set", "id": 2, "req": "peer", "key": "...", "name": "...", "addr": "10.10.33.5",
"endpoint": ["1.2.3.4", 5000], "sub_args": {...}, "force": false}` —
поля, которых нет, не меняются; с `"force": true` — очищаются.
Ошибки возвращаются строкой: `key_validate_error`, `key_ambiguous`, `name_not_str`, `addr_validate_error`,
`endpoint_validate_error`, `sub_args_not_dict`, `force_not_bool`.

`{"type": "del", "id": 3, "req": "peer" | "peer_endpoint", "key": "..."}` —
удалить пира или сбросить его текущее соединение. Ошибки: `peer_not_exist`, `error_delete_self_peer`.

### События

Узел рассылает всем клиентам `{"type": "event", "event": {...}}`:

* изменения пиров: `{"action": "add"|"update"|"del", "key", "name", "addr", "endpoint", "sub_args"}`;
* статус сервера: `{"server": [ip, port], "status": bool}`;
* новый замер ping: `{"key": "...", "ping": 12.3}`.

### Свои данные поверх сети (маршруты)

Клиент может занять номер маршрута от 32 до 255 и обмениваться через него произвольными данными с пирами:

```
{"type": "route", "id": 4, "req": "reg", "route": 40}      → nil или "route_exist" / "out_of_range"
{"type": "route", "id": 5, "req": "del", "route": 40}      → nil или "route_not_exist" / "not_permission"
{"type": "route", "id": 6, "req": "routes"}                → [40]
{"type": "net", "rou": 40, "key": "<кому>", "pack": b"данные"}
```

Пакет, пришедший от пира на маршрут 40, будет доставлен занявшему его клиенту в виде
`{"type": "net", "rou": 40, "key": "<от кого>", "pack": b"..."}`. Данные идут по той же сессии, что и IP-трафик.
Пакет должен помещаться в одну датаграмму: не больше ~1400 байт.

```
 a 192.168.1.2 ─ nat1 [masquerade + ct new drop] ─┐                ┌─ nat2 [...] ─ b 192.168.2.2
                                         203.0.113.11 ── «интернет» ── 203.0.113.12
                         сервер обнаружения 203.0.113.1:6485, c 203.0.113.20 (белый адрес)
```

  A создаёт группу, B и C входят по invite, за A и C — свои LAN, B ходит в интернет через C. Проверяется: сервер не отвечает на случайные пакеты, ping во всех направлениях, прямой путь nat1 → nat2 (hole punching, по счётчику nft),
  site-to-site между LAN за A и C, exit через C с переходом на A при недоступности C (оба — `[gateway]`), kill switch при недоступности обоих, DNS через шлюз, публичный IPv6 для B через NDP proxy на C, IPv6 внутри сети, отсутствие открытого текста на «интернете», маскировка (нет частого первого байта, ≥10 разных размеров
  на 30 одинаковых ping), iperf3, замена invite-сертификатов обычными, `node set` (новая подсеть и новый адрес доходят до всех), ACL (ping B→C запрещён, A→C разрешён), DNS и mDNS по именам участников, отзыв узла (исключённый узел отрезан,
  остальные связаны), смена psk после отзыва без разрыва связи, роуминг при смене внешнего адреса NAT
  (сессия с сервером его тоже переживает); затем всё останавливается, и новая группа связывается только по
  статическому адресу из invite, без сервера обнаружения; наконец два узла без единого IPv4-адреса находят друг
  друга через сервер обнаружения по IPv6 и связываются по IPv6; и mesh: MA и MC не видят друг друга, связь через
  ретранслятор, tracepath (IPv4 и IPv6) показывает ретранслятор, при его падении — через другой, при открытии
  прямого пути — напрямую; трекер останавливается, а изменение участника всё равно доходит до всех через соседей.

## Переход с версии 3.x

Версия 4 **несовместима** с 3.x ни по протоколу, ни по идентификаторам: сеть переводится целиком,
серверы обнаружения тоже нужно обновить.

1. **Сервер:** обновите бинарник; ключ сервера (`[local_server]`) сохраняется.
2. **Каждый участник:** обновите бинарник; в `config.toml` при первом запуске появится `[identity]` с новым
   ключом узла. Старые `[peer] peer_id` и `[net] addr` больше не используются (их можно удалить),
   `peers.json` не нужен.
3. **Организатор** создаёт группу (`dvpn group create`) и выдаёт каждому участнику invite (`dvpn group invite`),
   см. [Пошаговая настройка сети](#пошаговая-настройка-сети). Ключи шифрования пиров из 3.x не нужны.
4. Команды `set`, `del`, `list`, `export`, `import`, `export-peer`, `import-peer` убраны: участников и их адреса
   узел узнаёт из сертификатов.
5. **API:** поле `peer_id` везде заменено на `key`, запрос `get peer_id` — на `get key`; убраны `peer_crypto`
   и `crypto` в `set`; `peer_crypto_status` возвращает `"noise_ikpsk2"` или `"no"`;
   новые коды ошибок `key_validate_error`, `key_ambiguous`.

Переход с 2.x (Python) описан в README тегов `v2.*` и ветки `master`; сначала переходите на 3.x.

## Решение проблем

Для подробных логов поставьте `log_level = "DEBUG"` в `[app]`.

| Симптом | Причина и решение |
|---|---|
| `not in any group` | узел не в группе: `dvpn group create` или `dvpn group join <invite>` |
| `own certificate in group …: certificate expired` | срок истёк, а админ всё это время не был в сети: `dvpn group leave`, затем новый invite |
| `this node is revoked from the group` | узел исключён админом |
| `psk epoch N is active but there is no key for this node` | psk группы сменился, а ключ для этого узла не выдан (узел исключён, или админ не видел его в сети с момента входа): попросите у админа новый invite |
| `invite already used` в логе сервера | по этому invite уже вошёл другой узел: нужен новый invite |
| `invite expired` | invite просрочен (`--ttl`): попросите новый |
| `The clock is earlier than this build` | часы не выставлены (роутер без RTC до NTP): узел работает, но сервер обнаружения не ответит, пока время не установится; после NTP узел подключится сам. Админские команды до этого отказывают |
| `Connection status connecting` повторяется, `connected` не появляется | сервер недоступен или не совпадает ключ: проверьте `addr`/`port`/`key` в `[servers.*]`, открыт ли UDP-порт на сервере; сервер с другим ключом просто не отвечает (как и на любые чужие пакеты); часы узла расходятся с сервером больше чем на 10 минут — сервер тоже не ответит; если у сервера несколько IP — запустите его с `-a <публичный IP>` |
| сервер подключён, но пира не находит | пир не запущен или не подключён к тому же серверу; вы в разных группах (`dvpn group list`, сравните id) |
| `new endpoint` есть, но в DEBUG нет `session ... established` | разный профиль `[groups.obfs]` (поменялся у админа после выдачи invite) — или NAT не пробивается: симметричный NAT (часто мобильные сети, CGNAT) у обоих участников. Пробросьте порт на роутере у одного из них и задайте фиксированный `bind_port` |
| `packet ... with foreign source dropped` | пир шлёт пакеты не с адреса из своего сертификата (адрес на его TUN изменён вручную) |
| `Tun init error` | нет прав (root / `CAP_NET_ADMIN` / администратор), на Windows нет `wintun.dll` рядом с exe, либо интерфейс с таким именем уже занят |
| пинг идёт, но большие пакеты (сайты, файлы) зависают | уменьшите `mtu` в `[net]`, например до 1280 |
| оба участника за одним роутером не соединяются | роутер не поддерживает NAT hairpinning; в одной физической сети DVPN не нужен |
