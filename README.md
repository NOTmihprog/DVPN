# DVPN

> ### Что это вообще такое?
> Этот проект больше всего похож на [P2PVPN](http://www.p2pvpn.org/)
> и представляет собой шлюз, который создает **прямое соединение** до других пиров. <br><br>

> ### Для чего это можно использовать?
> Этот проект в первую очередь создавался для создания локальной сети в которой все участники сети находятся за nat и не имеют ipv6. <br><br>
> Для меня создание этого проекта решило проблемы с подключением к [Sunshine](https://github.com/LizardByte/Sunshine) на тех ПК которые находятся за nat
> и побочным эффектом стал упавший ping в [cs2](https://store.steampowered.com/app/730/CounterStrike_2/) в тех случаях когда хостом является участник сети, в моем случае ping упал с ~95 на ~30.

> ### Безопасность и анонимность
> Cтоит отметить что DVPN предназначен для создания именно локальных сетей,
> в которых участники сети знают друг друга, **не выкладывайте peer_id в открытый доступ**,
> это может привести в тому что кто угодно сможет получить доступ к вашей сети и представляться каким угодно пиром из вашей сети, <br>
> Если вашей целью является именно анонимность используйте [Yggdrasil](https://yggdrasil-network.github.io/) + [wireguard](https://www.wireguard.com/) или [i2p](https://geti2p.net/en/), [tor](https://www.torproject.org/).

## Как это работает

```
   пир A (за NAT)                 сервер обнаружения                 пир B (за NAT)
  ┌──────────────┐  announce/search  ┌─────────────┐  announce/search  ┌──────────────┐
  │ TUN 10.10.33.2│ ───────────────► │ dvpn server │ ◄─────────────── │ TUN 10.10.33.3│
  │    dvpn      │ ◄─── адрес B ──── │  UDP 6485   │ ──── адрес A ──► │    dvpn      │
  └──────┬───────┘                   └─────────────┘                   └──────┬───────┘
         │                                                                    │
         └──────────── прямой UDP-туннель (hole punching), шифрованный ───────┘
```

1. Каждый узел открывает **один** UDP-сокет и через него подключается к серверам обнаружения
   (handshake X25519, сервер подтверждает себя подписью Ed25519, дальше сессия ChaCha20-Poly1305).
2. Узел каждые 15 с сообщает серверу свой `peer_id` (announce) и просит адреса пиров из своего списка (search).
3. Когда два пира ищут друг друга, сервер одновременно сообщает каждому внешний адрес (IP:порт) другого.
4. Пиры начинают слать друг другу ping раз в секунду с того же сокета, это пробивает NAT (UDP hole punching).
   После первого ответа ping идёт раз в 15 с как keepalive; если пир молчит 45 с, соединение сбрасывается и поиск начинается заново.
   Если NAT собеседника выдал ему другой внешний порт, чем видел сервер, узел распознаёт пира по
   зашифрованному ping с нового адреса и переключается на него (roaming).
5. IP-пакеты из TUN-интерфейса отправляются напрямую нужному пиру (по его адресу в локальной сети),
   шифруясь XChaCha20-Poly1305. Сервер обнаружения трафик **не** пропускает через себя.

Сервер нужен только для знакомства пиров. Если он недоступен, уже установленные соединения продолжают работать.

## Сборка

Нужен Rust 1.85+ ([rustup.rs](https://rustup.rs/)).

```shell
git clone https://git.mihprog.com/DVPN/DVPN.git
cd DVPN
cargo build --release
# бинарник: target/release/dvpn (dvpn.exe на Windows)
```

### Linux

Для создания TUN-интерфейса нужны права root или capability `CAP_NET_ADMIN`:

```shell
sudo setcap cap_net_admin+ep target/release/dvpn   # чтобы запускать без sudo
```

Без root по умолчанию не получится создать unix-сокет API в `/run/dvpn`, тогда API автоматически
слушает `127.0.0.1:9902` (или укажите свой адрес через `-a`).

### Windows

1. Скачайте [Wintun](https://www.wintun.net/) и положите `wintun.dll` (из папки под вашу архитектуру,
   обычно `bin/amd64`) **рядом с `dvpn.exe`**.
2. Запускайте из консоли **от имени администратора**.
3. Разрешите `dvpn.exe` в брандмауэре Windows (входящий UDP), иначе пиры не смогут достучаться.

Кросс-сборка под Windows с Linux:

```shell
rustup target add x86_64-pc-windows-gnu
cargo build --release --target x86_64-pc-windows-gnu   # нужен mingw-w64
```

## Файлы и каталог данных

| Файл          | Назначение                                                          |
|---------------|---------------------------------------------------------------------|
| `config.toml` | настройки узла: свой peer_id, порты, серверы, TUN, уровень логов    |
| `peers.json`  | список пиров сети: имена, адреса в LAN, ключи шифрования            |

По умолчанию оба файла лежат **рядом с бинарником**. Другой каталог можно задать
опцией `--dir <путь>` или переменной окружения `DVPN_DIR` (действует для всех команд).

При первом запуске любой команды создаётся `config.toml` по умолчанию со случайным `peer_id`
и случайным адресом из `10.10.33.0/24`.

> Свой адрес в LAN хранится в `peers.json` (запись своего peer_id). Если он отличается от `[net] addr`
> в `config.toml`, при запуске значение в `config.toml` будет перезаписано из `peers.json`.

## Пошаговая настройка сети

Пример: сеть из двух участников, Алисы и Боба, и одного сервера обнаружения.

### 1. Сервер обнаружения

На машине с белым IP (VPS) — см. [Запуск сервера обнаружения](#запуск-сервера-обнаружения).
Запомните его **IP, порт и публичный ключ**.

### 2. Каждый участник: первый запуск и регистрация сервера

```shell
dvpn list            # создаст config.toml и покажет себя в таблице
```

Откройте `config.toml` и добавьте сервер:

```toml
[servers.main]
addr = "203.0.113.10"     # IP или доменное имя сервера
port = 6485
key = "lg9XXCn05ASLmw2QTu6R0F2Hy98SjvG70ByJUpLncw0="   # публичный ключ из вывода `dvpn server`
```

Серверов можно указать несколько (`[servers.msk]`, `[servers.am]`, …) — узел подключается ко всем.

### 3. Каждый участник: выдать себе адрес и ключ

```shell
dvpn set -p <свой_peer_id> -n alice -a 10.10.33.2 -k $(dvpn gen-key)
```

* `-p` — свой peer_id (виден в `dvpn list`, в квадратных скобках отмечена своя запись).
  Можно указывать только начало id, если оно однозначно: `-p kGaK`.
* `-a` — адрес в виртуальной сети, **уникальный** для каждого участника и из одной подсети (`[net] mask`).
* `-k` — ключ шифрования **входящего** к вам трафика. Все, кто шлёт вам пакеты, шифруют их этим ключом.

Затем экспортируйте свою запись и передайте её организатору сети (лучше по защищённому каналу —
строка содержит peer_id и ключ):

```shell
dvpn export-peer -o alice.txt
```

### 4. Организатор: собрать общий список

```shell
dvpn import-peer -i alice.txt
dvpn import-peer -i bob.txt
dvpn list
dvpn export -o peers.txt      # общий список всех участников
```

### 5. Каждый участник: импортировать общий список

```shell
dvpn import -i peers.txt      # без -i строку можно вставить в консоль
dvpn list
```

> **Важно:** у всех участников запись о каждом пире должна совпадать, в первую очередь ключ.
> Если у Алисы для Боба указан ключ, а у самого Боба своего ключа нет (или он другой),
> пакеты от Алисы Боб отбросит. После изменения ключа или адреса — заново раздайте `peers.txt`.

### 6. Запуск

```shell
sudo dvpn
```

В логах должно появиться `Connection status connected` (подключение к серверу), затем
`Peer bob(...) new endpoint 1.2.3.4:5678` и `receive pong`. Проверка:

```shell
ping 10.10.33.3
```

## Запуск сервера обнаружения

```shell
dvpn server                       # слушает 0.0.0.0:6485
dvpn server -a 0.0.0.0 -p 7000    # свой адрес и порт
```

При первом запуске сервер генерирует ключ Ed25519 и сохраняет его в `config.toml`:

```toml
[local_server]
private_key = "..."    # не передавайте никому
public_key = "..."     # этот ключ указывается у пиров в [servers.*] key
```

Публичный ключ также печатается в лог при каждом старте (`Public key: ...`).
Если удалить секцию `[local_server]`, будет создан новый ключ и его придётся обновить у всех пиров.

Откройте на сервере входящий **UDP**-порт (например, `ufw allow 6485/udp`).

> Если у сервера **несколько IP-адресов**, запускайте его с `-a <публичный IP>` — тем же адресом,
> что указан у пиров в `[servers.*] addr`. При `0.0.0.0` ядро может отправить ответ с другого адреса,
> и NAT клиента такой ответ отбросит (клиент застрянет в `connecting`).

Сервер хранит всё только в памяти: сессии без announce дольше 45 с удаляются.
Сервер не видит трафик между пирами и не знает их ключей шифрования.

## Запуск как службы

### systemd (Linux)

Пример для узла, установленного в `/opt/dvpn`:

```ini
# /etc/systemd/system/dvpn.service
[Unit]
Description=DVPN node
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/opt/dvpn/dvpn --dir /opt/dvpn
RuntimeDirectory=dvpn
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```shell
sudo systemctl daemon-reload
sudo systemctl enable --now dvpn
journalctl -u dvpn -f
```

Для сервера обнаружения — то же самое с `ExecStart=/opt/dvpn/dvpn --dir /opt/dvpn server`
(root ему не нужен, можно добавить `User=dvpn`, если порт ≥ 1024).

## Справочник config.toml

```toml
[peer]
peer_id = "kGaKgKFXwAOrm1jBNhBo9NrJZJE1onPv"  # 32 символа [a-zA-Z0-9], сгенерировать: dvpn gen-peer-id
bind_addr = "0.0.0.0"       # локальный IPv4 для UDP-сокета
bind_port = "8647-9942"     # порт или диапазон ("8647" или "8647-9942")

[servers.main]              # любое количество секций [servers.<имя>]
addr = "203.0.113.10"       # IPv4 или домен
port = 6485
key = "..."                 # публичный ключ сервера, base64

[net]                       # если секции нет — узел работает без TUN (как с -d)
tun_name = "dnet"           # имя интерфейса (имя адаптера Wintun на Windows)
mtu = 1350
addr = "10.10.33.2"         # свой адрес в сети (см. замечание про peers.json выше)
mask = "255.255.255.0"      # маска или длина префикса: "24"

[app]
log_level = "INFO"          # TRACE, DEBUG, INFO, WARNING, ERROR (CRITICAL = ERROR)

[local_server]              # создаётся командой dvpn server
private_key = "..."
public_key = "..."
```

**Порт.** Если задан диапазон и все серверы стали недоступны, узел переходит на другой случайный
порт из диапазона — это помогает, когда провайдер или NAT «залип» на старом порте.
Одиночный порт удобен, если вы пробрасываете его на роутере (тогда соединение возможно даже со строгим NAT у собеседника).

**MTU.** Накладные расходы DVPN — 70 байт на пакет (IP + UDP + заголовок + тег шифрования).
1350 подходит почти везде, включая PPPoE и мобильные сети. Если есть проблемы с большими пакетами — уменьшите до 1280.

**Формат peers.json** (редактировать руками можно, но лучше через `dvpn set`):

```json
[
  {
    "peer_id": "kGaKgKFXwAOrm1jBNhBo9NrJZJE1onPv",
    "name": "alice",
    "addr": "10.10.33.2",
    "key": "5cckXpktFAIKzoMEybbeXsqjhyd9eSTIxFwW-QV1wKY="
  }
]
```

## Справочник команд

Глобальные опции: `--dir <путь>` — каталог с конфигами, `-h` — справка по любой команде.

| Команда | Описание |
|---|---|
| `dvpn` | запустить узел |
| `dvpn -d` | запустить без TUN-интерфейса (только связь с пирами и API) |
| `dvpn -a <адрес>` | адрес API: `127.0.0.1:9902` или путь к unix-сокету |
| `dvpn -v` | версия |
| `dvpn gen-peer-id` | сгенерировать peer_id |
| `dvpn gen-key` | сгенерировать ключ шифрования (32 байта, base64) |
| `dvpn list` | таблица пиров |
| `dvpn set -p <id> [-n имя] [-a адрес] [-k ключ] [-c] [-s]` | добавить пира или изменить его поля |
| `dvpn del -p <id>` | удалить пира (себя удалить нельзя) |
| `dvpn export [-j] [-o файл]` | экспорт всех пиров |
| `dvpn import [-i файл] [-c]` | импорт списка пиров |
| `dvpn export-peer [-p id] [-j] [-o файл]` | экспорт одного пира (по умолчанию себя) |
| `dvpn import-peer [-i файл]` | импорт одного пира |
| `dvpn server [-a адрес] [-p порт]` | сервер обнаружения |

Подробнее про `set`:

* значение `None` очищает поле: `dvpn set -p bob -k None` — отключить шифрование для Боба;
* `-c` / `--clear` — очистить все поля, которые не указаны в команде;
* `-s` / `--self` — сделать этот peer_id своим (пропишется в `config.toml`, адрес возьмётся из записи пира).

Экспорт по умолчанию — JSON, закодированный в base64 (одна строка, удобно пересылать);
`-j` / `--json` выводит обычный JSON. Импорт принимает оба варианта.
`import -c` перед импортом удаляет всех пиров, кроме себя.

## API

Узел предоставляет локальный API для внешних программ (GUI/TUI, свои сервисы поверх сети).
Транспорт — датаграммы msgpack:

* Linux, если включён TUN и есть права: unix-сокет `/run/dvpn/<tun_name>.sock`;
* иначе (и на Windows): UDP `127.0.0.1:9902`;
* свой адрес: `dvpn -a 127.0.0.1:9000` или `dvpn -a /path/to/api.sock`.

> Любой локальный пользователь, имеющий доступ к сокету, может управлять узлом. Не выставляйте API наружу.

### Подключение

Каждое сообщение — msgpack-словарь с полем `type`. Сначала клиент отправляет
`{"type": "init", "name": "my-app"}`; без этого на остальные запросы приходит `{"type": "close"}`.
Узел шлёт клиенту `{"type": "ping"}` раз в 15 с; клиент должен ответить `{"type": "pong"}`, иначе
примерно через 45 с соединение закрывается. Отключиться — `{"type": "close"}`.

Запросы `get` / `set` / `del` / `route` содержат произвольный `id`, ответ приходит как
`{"type": "res", "id": <тот же id>, "res": <результат>}`.

Пример на Python:

```python
import socket, msgpack
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.bind(("127.0.0.1", 0))
node = ("127.0.0.1", 9902)
s.sendto(msgpack.dumps({"type": "init", "name": "example"}), node)
s.sendto(msgpack.dumps({"type": "get", "id": 1, "req": "peers"}), node)
print(msgpack.loads(s.recv(65535)))   # {'type': 'res', 'id': 1, 'res': ['kGaK...', ...]}
```

### get

`{"type": "get", "id": 1, "req": "<запрос>", ...}`

| `req` | параметры | результат |
|---|---|---|
| `peer_id` | | свой peer_id |
| `peers` | | список peer_id |
| `peer_exist` | `peer_id` | bool |
| `peer_name`, `peer_addr` | `peer_id` | строка или nil |
| `peer_crypto` | `peer_id` | `{"key": ...}` или nil |
| `peer_sub_args` | `peer_id` | словарь доп. параметров или nil |
| `peer_sub_arg` | `peer_id`, `arg` | значение параметра |
| `peer_endpoint` | `peer_id` | `[ip, port]` или nil |
| `peer_status` | `peer_id` | есть ли прямое соединение |
| `peer_ping` | `peer_id` | RTT в мс (0, если неизвестен) |
| `peer_crypto_status` | `peer_id` | `"xchacha20poly1305"` или `"no"` |
| `servers` | | список `[ip, port]` |
| `server_status` | `addr: [ip, port]` | подключён ли сервер |
| `server_key` | `addr` | публичный ключ (bytes) |
| `server_last_announce`, `server_last_search`, `server_last_response` | `addr` | unix-время, 0 — никогда |
| `local_addr` | | `[ip, port]` UDP-сокета узла |

### set / del

`{"type": "set", "id": 2, "req": "peer", "peer_id": "...", "name": "...", "addr": "10.10.33.5",
"key": "...", "endpoint": ["1.2.3.4", 5000], "sub_args": {...}, "force": false}` —
поля, которых нет, не меняются; с `"force": true` — очищаются. Ключ можно передать и как `"crypto": {"key": ...}`.
Ошибки возвращаются строкой: `peer_id_validate_error`, `name_not_str`, `addr_validate_error`,
`endpoint_validate_error`, `key_validate_error`, `crypto_not_dict`, `sub_args_not_dict`, `force_not_bool`.

`{"type": "del", "id": 3, "req": "peer" | "peer_endpoint", "peer_id": "..."}` —
удалить пира или сбросить его текущее соединение. Ошибки: `peer_not_exist`, `error_delete_self_peer`.

### События

Узел рассылает всем клиентам `{"type": "event", "event": {...}}`:

* изменения пиров: `{"action": "add"|"update"|"del", "peer_id", "name", "addr", "endpoint", "crypto", "sub_args"}`;
* статус сервера: `{"server": [ip, port], "status": bool}`;
* новый замер ping: `{"peer_id": "...", "ping": 12.3}`.

### Свои данные поверх сети (маршруты)

Клиент может занять номер маршрута от 32 до 255 и обмениваться через него произвольными данными с пирами:

```
{"type": "route", "id": 4, "req": "reg", "route": 40}      → nil или "route_exist" / "out_of_range"
{"type": "route", "id": 5, "req": "del", "route": 40}      → nil или "route_not_exist" / "not_permission"
{"type": "route", "id": 6, "req": "routes"}                → [40]
{"type": "net", "rou": 40, "peer_id": "<кому>", "pack": b"данные"}
```

Пакет, пришедший от пира на маршрут 40, будет доставлен занявшему его клиенту в виде
`{"type": "net", "rou": 40, "peer_id": "<от кого>", "pack": b"..."}`. Данные шифруются так же, как IP-трафик.
Размер одного пакета ограничен размером UDP-датаграммы (~65 КБ, но лучше держаться в пределах MTU).

## Тестирование и производительность

### Как тестировалось

* **Юнит-тесты** (`cargo test`): handshake с сервером (в т.ч. отказ при чужом ключе сервера и коротком HELLO),
  защита от повторов, шифрование пакетов пиров, хранилище пиров, разбор и сохранение конфига с комментариями.
* **Локально без TUN** (`dvpn -d`, сервер и 2 пира на 127.0.0.1): подключение к серверу, взаимный поиск,
  зашифрованный ping, все запросы API, передача данных через маршрут API между пирами,
  падение сервера → таймаут через 45 с и смена порта → повторное подключение и обновление адресов (~1 с),
  корректное завершение по Ctrl+C (сервер получает Close), таймаут линка до пропавшего пира,
  импорт экспорта из 2.x.
* **Стенд с TUN и NAT в network namespaces**, без root (через user namespace, `unshare -Urn`):

```
peerA 192.168.1.2 ─ routerA [NAT+firewall] ─┐               ┌─ routerB [NAT+firewall] ─ peerB 192.168.2.2
                                 198.51.100.2 ── «интернет» ── 203.0.113.2
                                            сервер 198.51.100.1:6485
```

  Роутеры — Linux `MASQUERADE` с отбрасыванием незапрошенных входящих пакетов, как в OpenWrt и типовых
  домашних роутерах. Напрямую пиры друг друга не видят, связь только через туннель `dnet`.
* **Сценарий с переназначением порта:** пир A с публичным IP, пир B за NAT без firewall. NAT роутера B
  выдал B другой внешний порт (21000 → 46401), чем видел сервер; узел A распознал B по зашифрованному ping
  с нового адреса и переключился на него за 1 с (roaming).
* Сборка под Windows (`x86_64-pc-windows-gnu`) проверена только компиляцией, запуск на Windows не тестировался.

### Результаты

Стенд: ARM Cortex-A76/A55, все namespace и iperf3 на одной машине, iperf3 TCP через туннель, 5 с.

| | 2.x (Python) | 3.x (Rust) |
|---|---|---|
| Шифрование трафика | нет (см. ниже) | XChaCha20-Poly1305 |
| Пропускная способность A → B | 72 Мбит/с | 225–262 Мбит/с |
| Пропускная способность B → A | 72 Мбит/с | 235–243 Мбит/с |
| Ping через туннель | — | 0.3–0.6 мс |
| Туннель поднимается после старта | ~30 с | ~3 с |
| Переназначенный порт NAT | соединение не устанавливается | roaming, ~1 с |

Только шифрование (1400-байтные пакеты, одно ядро Cortex-A76, шифрование + расшифровка):
Python (AES-CBC + HMAC через OpenSSL) — 24 800 пакетов/с, Rust (XChaCha20-Poly1305) — 83 000 пакетов/с.
Бенчмарк: `cargo test --release -- --ignored --nocapture bench`.

На x86 с AVX2 цифры у Rust заметно выше; узким местом в этих тестах был общий процессор стенда, а не DVPN.

## Особенности и ошибки версии 2.x

Найдено при переписывании и тестировании, в 3.x исправлено:

* **Шифрование через CLI не включалось.** `set -k` и `import` / `import-peer` вызывали
  `set_peer(peer_id, name, addr, crypto)` позиционно, и ключ попадал в параметр `endpoint`
  (а `force=True` затем обнулял `crypto`). В `list` всегда было `disabled`, трафик между пирами шёл открытым.
* **Медленное установление соединения.** Сервер сообщал адрес только тому пиру, который искал вторым;
  первый узнавал его лишь при следующем поиске (до 45 с).
* **Не работало за NAT, переназначающим порт.** Пакеты с адреса, отличного от сообщённого сервером,
  отбрасывались, а неверный адрес держался до таймаута.
* **Переподключение к серверу.** Если клиент начинал новую сессию с того же адреса, пока на сервере жила
  старая, сервер не мог расшифровать его пакеты, и клиент ждал до 45 с, пока сервер удалит старую сессию.
* **Нет защиты от повторов** в сессии с сервером; HELLO был меньше ответа сервера (усиление трафика
  при подмене адреса).
* **Подмена источника.** Пир мог отправить в TUN собеседника IP-пакет с чужим адресом отправителя.
* **Производительность.** Каждый пакет проходил 4 очереди между потоками (TUN → Router → Crypto → Peer) под GIL; на узел больше 10 потоков.
* **TUN в контейнерах.** `TUNSETOWNER`/`TUNSETGROUP` на uid 1000 падали в user namespace и контейнерах.
* **Мелочи:** обработчик события `update` в TUN не обновлял `ID2LADDR`; ошибки валидации в `config.py` создавались, но не выбрасывались
  (`ItemNotValidError(...)` без `raise`), поэтому неверные `addr`/`mask` в конфиге не обнаруживались.

## Переход с версии 2.x (Python)

Версия 3 **несовместима по протоколу** с 2.x: узлы 2.x и 3.x не видят друг друга,
серверы обнаружения тоже нужно обновить.

1. **Сервер:** запустите `dvpn server` версии 3 и раздайте участникам новый публичный ключ
   (теперь Ed25519, старые ключи Ed448 не подходят).
2. **Пиры:** в старой версии выполните `python main.py export -o peers.txt`,
   в новой — `dvpn import -i peers.txt`. Старый формат экспорта (`crypto.key`, `id`) поддерживается.
   **Шифрование, скорее всего, придётся настроить заново:** в 2.x команды `set -k` и `import` из-за ошибки
   не сохраняли ключ (в `list` было `disabled`), то есть трафик шёл без шифрования. Выдайте ключи
   через `dvpn set -p <id> -k $(dvpn gen-key)` и раздайте обновлённый список (см. шаги 3–5 выше).
3. **Конфиг:** `config.ini` заменён на `config.toml` с теми же параметрами. Имена ключей теперь
   через `_` (`peer-id` → `peer_id`, `bind-addr` → `bind_addr`, `tun-name` → `tun_name`, `log-level` → `log_level`),
   секции в нижнем регистре (`[Peer]` → `[peer]`, `[NET]` → `[net]`, `[App]` → `[app]`,
   `[Server.msk]` → `[servers.msk]`). Проще всего удалить старый конфиг, запустить `dvpn list` и перенести значения,
   в первую очередь `peer_id`.
4. **API** сохранён; изменился только ответ `peer_crypto_status` (`"xchacha20poly1305"` вместо `"symmetric"`)
   и добавились коды ошибок `endpoint_validate_error`, `key_validate_error`.

## Решение проблем

Для подробных логов поставьте `log_level = "DEBUG"` в `[app]`.

| Симптом | Причина и решение |
|---|---|
| `Connection status connecting` повторяется, `connected` не появляется | сервер недоступен или не совпадает ключ: проверьте `addr`/`port`/`key` в `[servers.*]`, открыт ли UDP-порт на сервере; при неверном ключе в логе `Reg session Invalid Signature`; если у сервера несколько IP — запустите его с `-a <публичный IP>` |
| сервер подключён, но пира не находит | пир не запущен, не подключён к тому же серверу или его нет в вашем `peers.json` (и вас — в его); проверьте `dvpn list` у обоих |
| `new endpoint` есть, но `receive pong` нет | NAT не пробивается: симметричный NAT (часто мобильные сети, CGNAT) у обоих участников. Пробросьте порт на роутере у одного из них и задайте фиксированный `bind_port` |
| `decrypt error` | у отправителя записан не тот ключ для вас: раздайте актуальный `peers.txt` |
| `encryption mismatch` | у одной стороны для получателя есть ключ, у другой нет — записи в `peers.json` расходятся |
| `packet ... with foreign source dropped` | пир шлёт пакеты не со своего адреса: у него в `peers.json` другой `addr` для себя |
| `TUN init error` | нет прав (root / `CAP_NET_ADMIN` / администратор), на Windows нет `wintun.dll` рядом с exe, либо интерфейс с таким именем уже занят |
| пинг идёт, но большие пакеты (сайты, файлы) зависают | уменьшите `mtu` в `[net]`, например до 1280 |
| оба участника за одним роутером не соединяются | роутер не поддерживает NAT hairpinning; в одной физической сети DVPN не нужен |
